# 抽菸行為偵測系統(Channel-as-Temporal-Buffer)

不依賴香菸物件、**純動作時序分析**的抽菸行為偵測系統。不偵測「菸」這個
在監控距離下只有幾個像素的小物件,而是偵測「抽菸這個動作序列」:
舉手靠近嘴 → 停留吸食 → 放下 → 週期性重複。

開發環境:單張 NVIDIA RTX 2060(6GB VRAM),Python + PyTorch 2.x。
架構全程只用 2D 卷積算子,保留向邊緣 NPU(Jetson Nano / STM32N6)移植的相容性。

> **接手這個專案(人或 AI)請先讀
> [`docs/專案現況與後續計畫.md`](docs/專案現況與後續計畫.md)** ——
> 現況總表、資料瓶頸、後續計畫、已知地雷與設計決策全在那一份。
> 本 README 是功能與方法的總覽。

## 這個系統現在能做什麼

一支 GUI(`啟動GUI.bat`),視窗最下方兩個分頁:

| 分頁 | 做什麼 |
|---|---|
| **即時偵測** | 讀影像來源 → 偵測追蹤 → 判定抽菸 → 警報與二次複核 |
| **直播錄影** | 把**直播**原樣存檔(不解碼、不掉幀),供事後離線分析 |
| **影片下載** | 把**影片**下載存檔(yt-dlp),供離線標記與訓練 |

兩者可同時開著:錄影不解碼,不吃 GPU 也不跟偵測搶 CPU。

### 分頁一:即時偵測

**影像來源**(來源欄直接填):

| 來源 | 範例 |
|---|---|
| 攝影機 | `0` |
| 影片檔 | `demo_videos/抽菸_特寫8秒.avi`(或按「瀏覽…」) |
| RTSP | `rtsp://admin:@pass@10.0.0.1:554`(原始密碼直接貼,含 `@` 自動編碼) |
| YouTube | `https://www.youtube.com/watch?v=…`(需 `pip install yt-dlp`) |
| HTTP 串流 | `https://…/live.m3u8` |

**判定方法**由控制列的下拉選單切換,共 7 種(見[下一節](#判定方法gui-可切換))。
預設「純規則」不需任何權重檔。**切換方法時會跳出參數視窗**,也可以按
「⚙ 參數」隨時打開:

- 逐項調整在場型態、手到嘴事件、警報、骨架規則、移動排除、複核門檻
  (每項旁邊寫了它是什麼、調了會怎樣)
- **只顯示這個方法真的會用到的參數** —— 純規則不會列融合權重,調了也沒用
- **每個方法各記各的**:調鬆 `rule` 不會連帶改到 `hybrid`,否則橫向比較
  比的就不是方法而是「最後一次動到誰」
- 存在 `configs/gui_overrides.json`(個人校準,不進版控),**yaml 保持原樣**
- 即時偵測與影片分析吃**同一份**設定 —— 先前分析是自己重讀設定檔的,
  畫面上調好的門檻它吃不到,標記位置與畫面行為對不起來

**追蹤狀態三欄**——由左到右就是一個人被處理的順序:

| 欄位 | 收誰 | 顯示 |
|---|---|---|
| 在場(經過·徘徊) | 還在**動**的人 | `ID11 徘徊 S2嘴部 背向 1次` + P 條 |
| 等待·待確認 | **停下來不動**、還沒判定抽菸 | `ID22 2次 警戒中 背向` |
| ⚠ 偵測到抽菸 | 警報成立中 | `ID31 P0.82 4次 [待複查]` |

「等待」欄才是真正的候選:**抽菸是站定了才做的事,走過去的只是路過**。
各欄固定格數,偵測閃爍時清單不會上下跳動。

**主畫面只有四個開關**(抽菸警報 / 徘徊警報 / 等待警報 / 骨架可視化)——
所有門檻數值都在方法的參數表裡。先前兩邊都能設「次數」,而主畫面會在管線
建好後立刻覆蓋參數表的值,等於參數表白設,兩邊還互相矛盾。

**下方左右分開**:左邊「警報片段」只列檔名與縮圖(雙擊播放),右邊「診斷
訊息」放停留秒數、計入/排除原因等過程資訊。警報是結果、診斷是過程,混在
同一個清單時校準訊息會把真正的警報洗掉。

**判定與排除**:

| 機制 | 說明 |
|---|---|
| 停留時長三分類 | < 2 秒 = 扶眼鏡(不計)、2–5 秒 = 抽菸的一口(計一次)、> 5 秒 = 講電話(不計) |
| 次數主導通報 | 有效事件 ≥ N 次(GUI 可調)且無排除條件 → 直接驅動警報,不被融合分數綁架 |
| 排除條件 | 背向棄權、**移動排除**(累積移動 ≥ 3 倍身高)、講電話姿態 |
| ⚠ 移動排除的副作用 | 預設開啟,走動中不發抽菸警報(走路手臂擺動很像手到嘴)。**因此經過與徘徊的人幾乎不會被判抽菸,只有停下來的(等待)會**。邊走邊抽的場景請到 ⚙ 參數關掉 |
| 距離自適應 | 腕-鼻距離以身體尺度正規化;太遠(< 24px)棄權;門檻附像素誤差餘裕 |
| 在場型態 | 經過(走/跑)、徘徊、等待——純軌跡幾何,不用模型也不需人標 |
| 第二階段複核 | 警報後用骨架時序複核,**降級不否決**(見[下方](#第二階段複核降級不否決)) |

**分流警示(不通報但不靜默)**:背向且網路高分 → 橘色「無法確認」並存 hard case;
長時間在場 + 看不到手 + 位移小 → 橘色「逗留」。

**校準與記錄**:診斷框顯示每段停留的秒數與計入/排除原因、「接近但差多少」;
警報自動錄「前 10 秒 + 後 4 秒」mp4(來源在後 4 秒內就結束時**寫短的而不是丟掉**),雙擊清單可回放;可選「乾淨影像」
(不烙印骨架線,供外觀模型訓練)並同步輸出節點序列 npz。

### 分頁三:影片下載

貼網址 →「查詢資訊」看標題/長度/大小 →「開始下載」。存成
`<資料夾>/<標題> [<影片id>].mp4`,可隨時取消、中斷可續傳。

**與「直播錄影」的分工只有一件事:來源會不會結束。**

| | 有沒有結尾 | 用哪個 |
|---|---|---|
| 直播 | 沒有 | 直播錄影(「讀不到 = 斷線,重連」成立) |
| 影片 | 有 | 影片下載(錄影器那個假設會變成無限重錄同一支) |

所以下載分頁在開始前會先問來源是不是直播,是的話直接擋下並請你改用錄影
分頁——不然它會一直下到磁碟滿。

畫質可選 360/480/720/1080。**720p 以上需要影音合流**(現代 YouTube 只有
360p 是影音已合流的漸進式格式,更高畫質是 DASH 分離),合流用的 ffmpeg
已內建(`imageio-ffmpeg`),不必另外安裝或動 PATH。

下載的檔案可直接餵回本專案:`VideoSource` 當一般影片檔讀(已驗證)。

### 播放器(`ui/player.py`)

下載清單與警報記錄雙擊都是開這個。功能是為**標記抽菸資料**選的,不是為了看片:

| 功能 | 為什麼需要 |
|---|---|
| 播放/暫停、可拖曳進度條、時間 | 反覆看同一口動作的基本盤 |
| 逐幀(`,` `.`)、0.25x～2x | 判準是「停留 2–5 秒」與舉手→停留→放下的轉折,正速看不清楚 |
| **開啟即分析** | 點開影片會**先跑一次判定再播放**:一趟同時產出抽菸位置與骨架。分析大約要影片長度的 **1 倍**時間(偵測器得跑過整支片;姿態偵測批次化後實測 2.7 倍加速),所以對話框提供三條出口:**等它跑完**、**先播放**(分析丟到背景,標記邊跑邊出現)、**不分析**。結果存成側車檔(`.analysis/<檔名>.npz`,**原始影片完全不動**),同一支第二次開是秒開(17s → 0.46s) |
| **標記軸** | 播放器下方獨立一條軸,每個標記是一個**可以按的點**(紅=分析偵測到、黃=手動標的),按下去直接跳過去 |
| **骨架疊加**(可開關) | 畫分析時存下來的關鍵點,查表而已 —— **不影響播放速度**。看見系統「看到的」腕-鼻幾何,誤判時一眼分辨是姿態估計錯還是規則錯 |
| 手動標記 | 偵測漏掉的地方自己補一個(黃點) |
| 截圖(`S`) | 存成 jpg,檔名帶幀號,可當論文插圖或誤判證據 |
| 全螢幕、循環開關、快捷鍵 | 空白=播放/暫停、`←→`=±5 秒、`N`/`P`=下/上一個標記、`F`=全螢幕 |

分析用的是主視窗「方法」選單當下選的那個方法,所以標記位置與即時偵測的
行為一致。骨架照分析的取樣率(預設 10fps)存,播放時往回取最近一個取樣點
——畫出來的就是系統判定時**真正看到**的那一組,不是另外補算的。
播放維持真正的 1x:解碼與繪圖的時間會從等待裡扣掉,追不上時丟幀保同步。
**60fps 的片子是難關**(每幀只有 16.7ms):修正前 1080p60 只有 0.36x,
現在 1.04x;1080p30 為 1.01x,開不開骨架都一樣。**沒有音訊**:畫面是 OpenCV 逐幀解碼的,判定用不到聲音,而無音訊
下逐幀與任意變速單純得多(有音訊就得處理音畫同步)。

> 取材請留意來源網站的服務條款與著作權;論文若要引用這些素材,
> 資料來源與去識別化最好寫清楚。

## 直播錄影(`scripts/record_stream.py`)

把直播原樣存到硬碟供事後離線分析。**全程不解碼**(ffmpeg `-c copy`),
其他性質都由這個決定推出來:

- **不掉幀** —— 寫進檔案的就是伺服器送來的封包,沒有解碼也沒有重編碼,
  中間沒有「來不及處理就丟掉」的環節(實測單段 900 幀 / 30.00 秒 @30fps,
  一幀不缺)。即時管線會掉幀是因為它必須邊解碼邊推理,錄影不需要
- **速度穩定** —— CPU 幾乎是零,瓶頸只剩磁碟與網路
- **殘檔仍可播** —— 輸出 `.ts`(mpegts)而不是 mp4:mp4 的索引寫在檔尾,
  行程被強制結束時整個檔案報廢,`.ts` 隨時砍掉都還播得動

也可以在 GUI 最下方切到「直播錄影」分頁操作(同一支 GUI)。命令列版本:

```bash
python scripts/record_stream.py "https://www.youtube.com/watch?v=xxxx" --root E:/recordings
python scripts/record_stream.py <url> --stats            # 看已錄內容與缺口
python scripts/record_stream.py <url> --prune-dry-run    # 看保留天數會刪掉哪些
```

```
E:/recordings/
  youtube_3nyPER2kzqk/        ← 依直播網址建立(同一直播固定同一資料夾)
    20260813/                 ← 每天一個,超過 --keep-days(預設 3)自動刪除
      20260813_215604.ts      ← 每段預設 10 分鐘
    20260814/                 ← 明天的**預先**建好,午夜才不會開檔失敗
    ffmpeg.log
```

> ⚠ **720p 實測約 21 MB/分 ≈ 30 GB/天**,保留 3 天要約 90 GB。啟動時會印出
> 磁碟可用空間並在不足時警告。`--root` 可指到別的磁碟。

跨日不重啟 ffmpeg(輸出路徑用 ffmpeg 的 `-strftime`),重啟只發生在連線真的
斷掉時,且每次重啟都會**重新解析** YouTube 網址 —— manifest 會過期。
`--stats` 的「缺口」欄是連線中斷期間真正缺掉的內容,與錄影機制無關。

錄下來的 `.ts` 可直接餵回本專案:`VideoSource` 當成一般影片檔讀。

## 判定方法(GUI 可切換)

清單來自 [`inference/methods.py`](inference/methods.py) 的登錄表,GUI 選單、
`python -m inference.pipeline --method`、`python scripts/gui.py --method`
三個入口都從同一份表長出來。**新增一種抽菸判定方法時,唯一要改的地方就是
在 `METHODS` 補一個 `Method`**,不必動 GUI 或管線——這是刻意的,方法散在
不同入口就沒辦法在相同條件下橫向比較。

| 代號 | 方法 | 判定含學習權重? | 說明 |
|---|---|---|---|
| `rule` | 純規則:骨架幾何 + 狀態機 | **否** | 腕-鼻距離判 S1/S2/S3、手到嘴次數決定警戒。**預設**;不需任何權重檔,換機器就能跑 |
| `rule+grammar` | 純規則 + 片段文法複核 | **否** | 警報後再以骨架時序的片段文法複核(手到嘴 0.4–3 秒、來回多次、貼嘴非貼耳) |
| `rule+l1grammar` | 純規則 + L1 網路基元 + 片段文法 | 是(L1) | 複核的逐幀基元改由訓練好的 L1(ST-GCN)給,深層仍是文法 |
| `rule+l1l2` | 純規則 + L1 + 學習版 L2 | 是(L1+L2) | ⚠ 6 段正樣本訓不動 L2,離線 AUC 0.58 < 文法 0.75,列著是為了對照 |
| `net` | 純外觀網路(CNN 時序) | 是 | 只由 cycle score 驅動警報,不套次數規則(基準線要乾淨) |
| `hybrid` | 外觀網路 + 規則融合 | 是 | 2026-07 的舊預設,`0.5×次數警戒 + 0.5×網路分數` |
| `hybrid+l1grammar` | 外觀網路 + 規則 + L1 + 片段文法 | 是 | 目前最完整的組合 |

```bash
python -m inference.pipeline --method list          # 列出全部方法與缺少的權重
python -m inference.pipeline --method rule --source 0
python scripts/gui.py --method rule+grammar        # 預選;啟動後仍可在選單改
```

「純規則」指的是**判定規則**不含學習權重:人物框與關鍵點仍然來自 YOLO,
但那是感測器(把畫面變成座標),不是在決定「這是不是抽菸」。

### 第二階段複核:降級不否決

含 `grammar` / `l1+...` 的方法會在紅色警報觸發時,把該對象**過去 90 秒**的
節點序列丟給第二階段(背景執行緒,不擋即時路徑),結果分三種:

| 狀態 | 意思 | 對警報的影響 |
|---|---|---|
| 已確認 | 複核也認為是抽菸 | 維持紅色 |
| 待複查 | 複核認為是別的動作 | **降為橘色**,警報仍在 |
| 無法複核 | 骨架看不到手,沒有足以判斷的輸入 | 維持紅色 |

「無法複核」不是湊出來的第三態:實測 47% 的片段鼻點可信幀不到 20%。若這種
情況也降級,等於因為攝影機角度不好就把真警報壓掉——那正是這個模組被明令
禁止做的事。降級門檻也刻意比升級寬(抽菸分數 ≥ 0.25 就不降級):誤降一次
真警報的代價遠高於多留一個橘色待複查。GUI 記錄裡雙擊複核那一列,會跳出
基元時間軸與節律統計,看得到系統憑什麼判。

## 方法

### 1. 核心:Channel-as-Temporal-Buffer 時序建模

每幀影像經共享權重的 2D backbone(ResNet-18 改 stride-8)產生 `C×H×W = 128×28×28`
特徵圖,推入**環形緩衝區**;推理時將最近 T 幀沿通道軸疊成 `(T·C)×H×W` 厚特徵圖:

```
通道排列(interleave):[c0t0, c0t1, ..., c0t15, c1t0, ...]
→ Conv2d(T·C → T·C, kernel=1, groups=C)   每組恰為同一特徵通道的 16 個時刻
                                            = depthwise temporal conv(攤平為 2D)
→ Conv2d(T·C → 256, kernel=1)              跨特徵語意混合
→ 2 個 3×3 conv block → GAP → 分類頭
```

- **純 2D 算子**:無 Conv3D / LSTM / attention(單元測試強制白名單)
- **Continual inference**:新幀只跑一次 backbone,僅重算時序頭,算力為滑動視窗重算法的 1/T
- **雙時間尺度**:短尺度 T=16, stride=1(單次動作約 2 秒)+ 長尺度 T=16, stride=8
  (週期重複約 13 秒),兩頭 embedding 融合輸出 cycle score

### 2. 骨架輔助分支(late fusion)

YOLOv8s-pose 一次前向同時取得人物框與 17 個 COCO 關鍵點:

- **腕-鼻正規化距離** `d = dist(腕, 鼻) / max(肩寬, 0.55×軀幹高)`
  (軀幹高對水平旋轉不變,補側面視角肩寬被壓縮的問題)
- 規則推斷階段:d 快速縮小 → S1;d < 0.9+誤差餘裕 → S2 手在臉部;自嘴部快速拉大 → S3
- **朝向判斷**:COCO 關鍵點有左右語意,背對時左右肩 x 順序顛倒(+ 鼻點置信度)
  → 背向時棄權,不產生 S2 訊號
- S2 停留(≥0.5 秒,容忍 0.5 秒偵測中斷)結算為一次「手到嘴事件」進入次數計數器

### 3. 動作語意分類(停留時長)

「手在臉部」是抽菸的必要非充分條件。以停留時長區分語意
(0.5 秒偵測中斷容忍,骨架閃爍不切碎停留):

| 停留時長 | 語意 | 處理 |
|----------|------|------|
| < 2 秒 | 戴耳機 / 扶眼鏡 / 摸臉 | 不計 |
| 2 ~ 5 秒 | 抽菸的一口 | 計一次事件(與上次間隔 ≥ 2 秒) |
| > 5 秒(未放下) | 講電話 | 不計,**即時**標示 PHONE 並關閉通報 |

### 4. 通報邏輯(次數主導)

```
有效事件次數(90 秒視窗):1 次 → 低 0.2、2 次 → 中 0.5、≥3 次 → 高 0.8
P_t = 0.9·P_{t-1} + 0.1·單週期分數          (EMA,per-track)

紅色警報 = 非背向 ∧ 非移動中 ∧ 非講電話 ∧ 有效事件 ≥ N(GUI 可調)
           → 分數直接推滿,P_t 持續超過觸發線 2 秒後通報
解除:P_t < 解除線(雙門檻 hysteresis);事件過期後自然衰退

設計說明:若僅做加權融合(0.4×次數 + 0.6×網路),次數分上限 0.8
使 P 上限 0.32 永遠過不了 0.6 觸發線,「N 次通報」形同虛設;
次數主導模式讓通報語意與使用者設定一致,網路分數保留為
顯示與未來重訓後的驗證訊號。
```

### 5. 在場型態:經過 / 徘徊 / 等待(刻意不用模型)

從框的軌跡直接算,量測一律以人物自身身高(框高)為單位,與攝影機距離無關:

```
累積路徑 = 中心逐幀位移總和 ÷ 平均框高      (走了多少)
位移範圍 = 起訖最大距離 ÷ 平均框高          (走多遠,來回會抵銷)

在場短 + 有移動        → 經過(速度超過門檻記為跑步)
在場久 + 累積路徑大    → 徘徊
在場久 + 累積路徑小    → 等待
```

**累積路徑與位移範圍分開看是關鍵**:原地來回踱步的人位移範圍很小、
累積路徑卻很大——這正是徘徊,只看位移會誤判成等待。

不交給模型的理由:這幾件事幾何上就是確定的,用模型學只會把「一個隨時
能調的門檻」變成「要重訓才能改的權重」。

已知限制:影像空間的量測,朝鏡頭正面走來的人位移看起來小,可能被判成
等待;根治需地面標定,目前以側向/俯視鏡位為前提。

## 第二階段:骨架時序過濾器(`stage2/`,進行中)

定位是**級聯驗證器**:第一階段維持高召回負責圈出候選,第二階段對候選做
離線二次檢測、過濾誤報。**降級不否決**——判非抽菸只把警報降為橘色
「待人工複查」,不取消,召回由結構保證不下降。離線執行,不受邊緣算子限制。

### 兩層骨架時序模型(2026-08,現行架構)

判斷不再由一個網路直接從骨架吐出「抽菸」,而是**先解析成看得懂的基元,
再由基元的序列組合出具體動作**。完整設計見
[`docs/兩層骨架時序模型設計.md`](docs/兩層骨架時序模型設計.md)。

```
節點序列 (T,17,3)
   ├─→ 拓樸圖特徵 (T,13,5)   平移+尺度正規化,不旋轉
   └─→ 運動學特徵 (T,45)     身體座標系裡的角度與距離,旋轉不變
         ▼  L1 PrimitiveNet(ST-GCN + 運動學支流,10 萬參數)
   逐幀基元:靜置 / 舉手 / 停留臉部 / 放下 / 其他活動        ← 淺層
         ▼  分段(片段帶 21 維屬性:時長、最小腕鼻距、肘角…)
   片段序列:[舉手 0.6s] [停留 1.2s, 腕鼻距 0.46] [放下 0.8s] …
         ▼  L2 CompositionNet(時間感知 Transformer,2 萬參數)
   具體動作:抽菸 / 喝水 / 講電話 / 扶眼鏡 / 抓頭髮 / 其他    ← 深層
```

**為什麼用拓樸圖**:攤平成向量之後「腕」與「膝」只是相鄰的兩個數字,
模型得自己學出「腕接肘、肘接肩」——幾十段資料學不出來。鄰接矩陣裡另外
加了**功能邊**(腕↔鼻、腕↔耳、腕↔眼):不是骨頭,但正是本任務的判別關係,
訊息一步就傳到。

**為什麼分兩層**:L1 的監督訊號由規則自動產生(17,338 幀×手,不用人標),
再多錄影片就自動變多;L2 的輸入被壓成十幾個 token,參數量壓到 2 萬,
才有機會用幾十段學起來。誤判時也看得到是哪一層錯。

**現在的數字**

L1 逐幀基元(5-fold,64 段):整體 0.707 ± 0.018;
舉手 0.82 / 停留臉部 0.90 / 放下 0.83 / 靜置 0.86(整體被概括類「其他活動」
0.52 拉低)。

抽菸維度 AUC(64 段,正樣本 6 段):

| 淺層 | 深層 | AUC |
|---|---|---|
| 規則 | 片段文法 | 0.733 |
| **L1 網路** | **片段文法** | **0.750** |
| L1 網路 | 學習版 L2 | 0.580 |

L2 學習版輸給無參數的文法,而且輸得不冤:**抽菸正樣本只有 6 段,學不動
2 萬個參數**。這是資料量的問題不是架構的問題,在補到足夠正樣本之前推論
不要載入 L2 權重(`HierarchicalRecognizer` 不給 `l2_ckpt` 就自動走文法;
`train_l2.py` 每次跑完會自己跟文法比一次並印出結論)。

**真正的瓶頸是姿態偵測,不是動作模型**:64 段裡有 **30 段(47%)**
鼻點可信的幀不到 20%;6 段抽菸正樣本中有 2 段的腕點可見率只有 4% 與 18%
——姿態模型根本看不到那個人的手臂,上面接什麼模型都判不出來。骨架看得清
的片段判得很乾淨(可見率 100% 的那段:四次「舉手 → 停留 1.8 秒 → 放下」,
抽菸 0.87)。

**標記類別(`stage2/taxonomy.py`)**:11 類(8 動作 + 3 排除),
深層併成 6 類 `smoking / drinking / phone_call / glasses / hair / other`。

粒度在 2026-08 放寬了:舊版把推眼鏡 / 抓頭 / 托腮全併成「手碰臉」,
因為在**逐幀攤平特徵**上它們確實是同一團點。深層看的是**片段**——
扶眼鏡是「眼睛高度、0.5–1 秒、幾乎不動」,抓頭髮是「眼睛以上、1–3 秒」,
在「停留位置 × 時長 × 速度」的空間裡分得開,所以拆成各自的按鈕。
判準沒變,變的是特徵的解析度。

**還缺什麼**:抽菸正樣本(唯一硬門檻)、喝水/講電話/扶眼鏡/抓頭髮各 0 段、
以及 60–90 秒長時窗——現有片段只有 13 秒,一根菸的節律根本放不進來。

### 舊版:攤平 PoseTCN(`stage2/model.py`,保留作對照)

```
節點序列 → M1 正規化(85 維攤平)→ M2 PoseTCN → 4 類
```

正規化後對**人在畫面的位置、離鏡頭遠近、身材高矮**皆不變(有單元測試
驗證)。已被上面的兩層模型取代,程式保留不動當對照組。

**純骨架的天花板**:單次「手到嘴」分不出抽菸與喝水/吃東西,要靠**節律**
(2–5 秒停留、規律重複多輪)才有辨別力。真正要分「手上拿的是菸、杯子還是
手機」得靠外觀分支,而那**依賴不烙印疊加層的乾淨錄影**(已實作為 GUI 開關)。

## 目前成果與已知問題

**資料**:HMDB51 子集(smoke/drink/eat/chew/talk 共 610 段),YOLO+ByteTrack
自動標註(僅 clip 級標籤,無幀級階段標籤)。

**Clip 級(驗證集 105 段)**:端到端微調後 accuracy 93.3%、macro-F1 0.86、
AUC 0.85;smoking recall 11/18;喝水/吃東西/講話 hard negative 零誤判。

**已知問題:實地(監控視角)不漏測但誤測偏多。** 根因分析:

1. **Domain gap**:網路以 HMDB51(電影片段、多為正面近景)訓練,對監控俯視角
   的一般動作(摸臉、喝水、講電話、托腮)常給出高分;實測背向辦公人員的網路
   分數常達 0.7–0.95(訓練集中沒有這類負樣本)
2. **骨架幾何的先天歧義**:「手在臉部區域」是抽菸的必要非充分條件,
   規則分支無法單獨區分摸臉/托腮
3. 已有的緩解(背向棄權、次數門檻、移動排除)壓低了誤報頻率,
   但**治本需要目標場景的自錄資料重訓**——系統已自動把「背向高分」案例
   存進 `hard_cases/`,即為重訓資料的來源

**第二階段資料現況(最大瓶頸)**:已標 87 段警報片段、回抽出 64 段節點
序列,其中**抽菸正樣本僅 6 段,而且有 2 段的腕點可見率只有 4% 與 18%**
(姿態模型看不到手臂),實際可用的正樣本是 4 段。全體 64 段裡有 30 段
(47%)鼻點可信的幀不到兩成。舊標籤裡 58 段 `other_neg` / `desk_work`
是 2026-07 的粗類,當二分類的負樣本可用,但裡面混著扶眼鏡與抓頭髮,
要訓練六分類前需以新清單複標。

**Roadmap**:
1. 自錄資料集——場域擺拍抽菸(5–8 人 × 站/坐 × 多角度,每段 2–3 分鐘
   完整過程含點菸),其餘負樣本靠常態錄製自然累積後標記。**唯一硬門檻**
2. **改善姿態可見度**:換鏡位/降低俯角。47% 的片段骨架不可用,
   這一項不做,再多資料也有一半是廢的
3. 以新的細類複標既有 58 段粗類負樣本 → 訓練 L2 六分類,
   上線量測誤報過濾率(主指標:固定 100% 正樣本召回下的誤報過濾率)
4. 重訓第一階段外觀網路與階段頭(需乾淨錄影)
5. 路 B 的 60–90 秒滾動節點緩衝 → 節律統計才有意義;加入外觀流
   分辨「手上拿的是菸、杯子還是手機」
6. 啟用狀態機順序驗證 → KD 蒸餾 → 事件級評估 FP/h
