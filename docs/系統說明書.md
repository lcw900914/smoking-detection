# 抽菸行為偵測系統 — 功能與方法說明書

版本:2026-07(對應 repo `master`,119 個單元測試)
環境:Python + PyTorch 2.x,單卡 NVIDIA RTX 2060(6GB VRAM)
Repo:https://github.com/lcw900914/smoking-detection(私人)

---

## 1. 系統概述

本系統**不偵測香菸物件**(監控距離下僅數像素、易遮擋、新型菸具外觀多變),
而是偵測「抽菸這個動作序列」:舉手靠近嘴 → 停留吸食 → 放下 → 週期性重複。

判斷單位是「人」:每位被追蹤到的人各自獨立累積證據,證據足夠才通報。
系統設計目標為**高召回(不漏測)**,誤測以多層排除條件與人工複查分流控制。

### 1.1 整體管線

```
影像來源(檔案 / 攝影機 / RTSP 串流)
  → YOLOv8-pose:人物框 + 17 個 COCO 關鍵點(一次前向)
  → ByteTrack 多人追蹤(每人一個 track ID)
  → 每 track:
      ├ 上半身 ROI(EMA 平滑框)→ 共享 backbone 特徵 → 雙尺度環形緩衝
      │   → 時序融合頭 → 網路分數(外觀分支)
      └ 骨架:腕-鼻正規化距離 → 停留時長分類 → 手到嘴事件計數(規則分支)
  → 通報邏輯:排除條件(背向/移動/講電話)+ 次數門檻 + 持續確認
  → 警報(紅)/ 無法確認(橘)/ 逗留警告(橘)+ 片段錄製與回放
```

### 1.2 實測效能(RTX 2060)

| 項目 | 數值 |
|------|------|
| 1080p@30fps RTSP 串流 | 特徵率 8.1 fps,單步中位 63ms,同時追蹤 4–5 人 |
| Clip 級(HMDB51 驗證集 105 段) | Acc 93.3%、Macro-F1 0.86、AUC 0.85;喝水/吃/講話零誤判 |
| 警報行為 | 第 2 次有效停留後約 3 秒通報 |
| 背向誤報(90 秒實測,78% 背向) | 紅色警報 0 次 |

## 2. 功能總覽

### 2.1 偵測與判定

| 功能 | 說明 |
|------|------|
| 多人即時偵測 | 每人獨立的緩衝、計數、警報狀態;track 消失 3 秒自動回收 |
| 停留時長三分類 | 手在臉部停留 < 2 秒 = 戴耳機/扶眼鏡(不計);**2~5 秒 = 抽菸的一口(計一次)**;> 5 秒未放下 = 講電話(不計,即時標示 PHONE) |
| 次數警戒等級 | 90 秒視窗內有效事件:1 次 → 低(0.2)、2 次 → 中(0.5)、≥3 次 → 高(0.8) |
| 次數主導通報 | 事件次數 ≥ N(GUI 可設)且無任何排除條件 → 分數直接推滿,持續 2 秒確認後通報 |
| 「由遠而近」武裝 | S2 只在手曾離臉夠遠(或腕點持續不可見 0.5 秒)後採信;每口之間須重新武裝——阻擋手被遮擋時姿態模型的高置信腕點幻覺 |

### 2.2 排除條件(任一成立即不通報紅色)

| 條件 | 判定方式 | 目的 |
|------|----------|------|
| 背向 | 肩膀左右順序顛倒(COCO 關鍵點左右語意)+ 鼻點置信度;近 5 秒背向幀 ≥60% | 背向時 2D 腕-鼻距離無意義,骨架棄權 |
| 移動中(可開關) | 10 秒視窗累積移動 ≥ 3 倍自身框高(以人物尺寸為單位,與鏡頭距離無關) | 走動時手部擺動易誤判 |
| 講電話 | 手舉著超過 5 秒未放下(即時判定,不必等放下) | 長時間手在臉部 ≠ 抽菸 |

### 2.3 分流警示(不通報但不靜默)

| 警示 | 觸發條件 | 顏色 |
|------|----------|------|
| 無法確認(UNVERIFIED) | 背向 且 網路分數 ≥ 0.7 | 橘 |
| 逗留警告(LOITER) | 在場 ≥20 秒 + 手腕可見率 ≤10% + 位移小 | 橘 |

無法確認案例自動存 `hard_cases/`(每 track 30 秒冷卻),作為日後重訓的負樣本來源。

### 2.4 介面與記錄

| 功能 | 說明 |
|------|------|
| Demo GUI | 影像隨視窗縮放;所有門檻即時調整 |
| 追蹤狀態三欄 | **在場(經過·徘徊)**:還在動的人,ID + 徘徊/經過 + 階段/次數/背向;**等待·待確認**:停下來不動、但還沒判定抽菸的人 —— 這一欄才是真正的候選;**⚠ 偵測到抽菸**:警報成立者(含第二階段複核結果)。各欄固定格數,偵測閃爍時清單不跳動 |
| 骨架可視化 | 關鍵點、骨架連線、腕-鼻距離線(S2 時紅色加粗並標距離值) |
| 警報記錄 | 條列式分頁(每頁 8 筆,可跳頁);預設只顯示警報項目 |
| 片段回放 | 警報自動錄「前 10 秒 + 後 4 秒」mp4(`alarms/clips/`);雙擊警報項目開回放視窗,畫面隨視窗縮放 |
| 診斷模式(可開關) | 顯示每段停留的秒數與計入/排除原因、「接近但未達門檻差多少」等校準訊息 |
| RTSP 串流 | 憑證特殊字元自動編碼(密碼含 @ 直接貼)、強制 TCP、只保留最新影格(延遲不累積)、斷線自動重連 |
| YouTube / m3u8 | 貼網址即可(YouTube 用 yt-dlp 解析,重連時自動重新解析);時間戳取自串流 PTS 而非牆鐘,HLS 的分段抵達才不會把停留秒數壓扁 |

## 3. 方法原理

### 3.1 外觀分支:Channel-as-Temporal-Buffer

每幀影像經共享權重的 2D backbone(ResNet-18 改 stride-8,輸出 128×28×28)
產生特徵圖,推入環形緩衝;推理時把最近 T 幀沿**通道軸**疊成 (T·C)×H×W:

```
通道排列(interleave):[c0t0, c0t1, …, c0t15, c1t0, …]
→ Conv2d(T·C → T·C, kernel=1, groups=C)   ← 每組恰為同一特徵通道的
                                             T 個時刻 = 時間卷積攤平為 2D
→ Conv2d(T·C → 256, kernel=1)              ← 跨特徵語意混合
→ 2 × Conv3×3 block → GAP → 分類頭
```

- **純 2D 算子**:全模型只含 Conv2d/BN/activation/pooling/Linear
  (單元測試強制白名單),保留向 Jetson / STM32N6 等邊緣 NPU 移植性
- **Continual inference**:新幀只跑一次 backbone、僅重算時序頭,
  算力為滑動視窗重算法的 1/T
- **雙時間尺度**:短尺度 T=16, stride=1(單次動作 ~2 秒)+
  長尺度 T=16, stride=8(週期重複 ~13 秒);兩頭 embedding 融合出 cycle score
- 訓練端 dataset 疊合與推理端 ring buffer 共用同一 layout 函式,
  以單元測試鎖定兩路徑逐元素一致

### 3.2 骨架分支:腕-鼻距離的規則判定

YOLOv8-pose 一次前向同時給出人物框(餵追蹤)與 17 個關鍵點:

**距離正規化(距離不變性)**
```
d = dist(腕, 鼻) / max(肩寬, 0.55 × 軀幹高)
```
- 除以身體自身尺度 → 近處人像素距離大但肩寬也大,比值不變
- 軀幹高(肩中點→髖中點)對水平旋轉不變,補側面視角肩寬被透視壓縮的問題
- 太遠(尺度 < 24px)棄權——關鍵點量化誤差會淹沒真實距離
- 門檻自適應:`near_eff = 0.9 + 4px/尺度`,越遠自動放寬誤差餘裕
- 門檻語意是「手在**臉部區域**」(0.9):持菸時指尖碰唇,腕距鼻仍有
  一掌 + 菸長,0.6 的「貼嘴」門檻會漏

**階段推斷**:d 快速縮小 → S1 舉手;d < near_eff → S2 手在臉部;
自臉部快速拉大 → S3 放下。

**「由遠而近」武裝機制(anti-hallucination)**
手被遮擋(背在身後/插口袋)時,姿態模型會以高置信度(實測 0.83–0.98,
置信度門檻無效)把腕點幻覺在身體輪廓上,距離恰落在門檻內。
真動作與幻覺的本質差異:**真的吸一口,手必先從遠處舉起;幻覺點恆定
懸停,從不先遠離再靠近**。因此:

- S2 只在「武裝」狀態下採信:d 曾 ≥ near+0.5,或腕點/姿態持續不可見
  ≥0.5 秒(手垂下出畫面的等效遠離;幻覺點恆定可見走不了這條路)
- 進入 S2 即消耗武裝;每口之間手須放回遠處重新武裝
- 任何棄權路徑(背向/太遠/無姿態)中斷 ≥0.5 秒即清除進行中的 S2
  狀態(防狀態洩漏);短暫抖動(1–2 幀)不切碎真動作

**朝向判斷**:COCO 關鍵點有左右語意——正對鏡頭時人的右肩(kpt 6)
在畫面 x 較小側,背對時顛倒;搭配鼻點置信度(≥0.5,背面幻覺鼻點
多過不了)。肩距分離不足(側面)時不判背向,回退鼻點規則。

### 3.3 事件計數與通報

**手到嘴事件**:一段 S2 停留(容忍 ≤0.5 秒偵測中斷)結束時結算——
停留 2~5 秒且與上次事件間隔 ≥2 秒才計一次;過短(扶眼鏡)與過長
(講電話)皆不計,並回報原因供診斷。

**通報邏輯(次數主導)**:
```
紅色警報 = 非背向 ∧ 非移動中 ∧ 非講電話 ∧ 有效事件 ≥ N
           → 分數推滿,P_t(EMA α=0.9)持續超過觸發線 2 秒後通報
解除:P_t < 解除線(雙門檻 hysteresis,防抖);事件過期(90 秒)自然衰退
```
設計說明:若僅做加權融合(0.4×次數 + 0.6×網路),次數分上限 0.8 使
P 上限 0.32,永遠過不了 0.6 觸發線——「設 N 次通報」形同虛設。
次數主導讓通報語意與設定一致;網路分數保留為顯示與(重訓後的)驗證訊號。

### 3.4 訓練配方(6GB VRAM)

1. **離線特徵**:凍結 backbone 抽全資料集特徵存 fp16 .npy
2. **階段一**:只訓練時序頭(batch 128–256,不碰影像)
3. **階段二**:端到端微調(AMP + batch 8 × grad accum 4 + backbone lr×0.1)
4. **離線蒸餾**(管線已備妥):X3D-M teacher 預計算 soft labels 落地,
   師生絕不同時佔用 VRAM

資料:HMDB51 子集(smoke/drink/eat/chew/talk 共 610 段),
以本系統的偵測+追蹤管線自動產生人物框標註(`scripts/auto_annotate.py`)。

## 4. 操作手冊

### 4.1 安裝與啟動

```bash
pip install -r requirements.txt      # GPU 請裝對應 CUDA 的 torch/torchvision
# Windows 若遇 OMP Error #15:set KMP_DUPLICATE_LIB_OK=TRUE

```

**來源欄位**可填:

| 來源 | 範例 |
|---|---|
| 攝影機編號 | `0` |
| 影片檔 | `demo_videos/抽菸_特寫8秒.avi`(或按「瀏覽…」) |
| RTSP | `rtsp://admin:@admin888@192.168.11.197:554`(原始密碼直接貼,含 @ 會自動編碼) |
| YouTube | `https://www.youtube.com/watch?v=xxxxxxxxxxx`(直播或一般影片,需 `pip install yt-dlp`) |
| HTTP 串流 | `https://.../live.m3u8`(公開的 m3u8 直播直接貼) |

YouTube 與 m3u8 的注意事項:

- **延遲大**(YouTube 直播本身 5–30 秒 + HLS 分段緩衝),適合當測試素材,
  不適合真的即時通報
- 手邊沒有攝影機時,拿公開街景直播來試整條管線很方便;但要知道那類畫面
  的人通常很小、多半背向,骨架分支會大量棄權,**看到「不通報」是正常的,
  不代表系統壞了**
- **狀態列會顯示實際速率**,例如 `執行中 9.8 fps 佇列14 落後比1.16`:
  - 速率:實際每秒推理幾次(目標 10)
  - 佇列:緩衝裡還有幾幀。長期是 0 → 來源餵不夠
  - 落後比:消化的串流秒數 ÷ 牆鐘秒數。<1 表示正被直播拉開
- 系統會**刻意落後直播邊緣約 5 秒**(`stream.prefill_sec`),先囤一段再開始
  消化,並照 1× 速度供幀。HLS 是「一段送完就空等」,不這樣做畫面會一頓
  一頓。實測 90 秒:未囤 2.0 fps → 囤+節流 **9.6~12.2 fps,卡頓從 18 次
  降到 3 次**。要更穩可以把 `prefill_sec` 調大(代價是延遲同步增加)
- ⚠ **調低 `stream.max_height` 不會變快。** YOLO 內部一律把畫面縮到
  imgsz=640,實測 720p 與 480p 的偵測都是 27 ms,只差解碼的那 2 ms
- 終端出現一堆 `Cannot reuse HTTP connection for different host` 是 FFmpeg
  的良性訊息(YouTube 每換一次 CDN 主機就印一行,它自己會重連)。
  用 `啟動GUI.bat` 啟動的話已經導進 `logs/gui_stderr.log`,主控台看不到;
  直接下命令列想安靜就自己接 `2>nul`

## 6. 已知限制與後續規劃

**目前狀態:不漏測,誤測經多層排除後仍偏多。** 根因:

1. **Domain gap**:外觀網路以 HMDB51(電影片段)訓練,對監控俯視角的
   一般動作常給高分(訓練集無此類負樣本)
2. **「手在臉部」先天歧義**:規則分支無法單獨區分抽菸/喝水的單次動作
3. **單目 2D 物理極限**:背向的手到嘴不可驗證(已分流為橘色警示)

**規劃中:第二階段節律驗證(級聯)**——第一階段維持高召回並錄下候選
片段;第二階段對候選 track 的 bbox 序列做長時窗(1–3 分鐘)時序行為
辨識:每個事件的外觀嵌入(Level A)+ 事件序列的節律模型(Level B)。
判定「非抽菸」時**降級**為橘色待複查、不硬否決(召回結構性不掉);
確認才升紅色。前置需求:目標場域的抽菸正樣本(系統已自動累積
hard negative 於 `hard_cases/`)、track 連續性(必要時補輕量 re-ID)。

其後:重訓外觀網路與階段頭 → 啟用 S1→S2→S3 狀態機驗證 →
知識蒸餾(M5)→ 事件級評估 FP/h(M6)→ 邊緣部署。
