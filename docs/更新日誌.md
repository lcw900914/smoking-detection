## 未修正的演算法問題(2026-08-16 稽核)

上一輪查的是工程缺陷,這一輪查**判定邏輯本身**。標「已量化」的附了可重跑的
數字,標「推論」的只由程式碼推得。這些多半不是「壞掉」,而是**方法上站不住
腳**——論文寫下去會被問的那種。同樣尚未動手修。

### 🔴 A1 累積路徑把偵測抖動當成移動,靜止的人會被判成徘徊(已量化)

`PresenceClassifier._metrics()` 用**逐幀位移的總和**當「走了多少」:

```python
for (_, x0, y0, _), (_, x1, y1, _) in zip(pts, pts[1:]):
    path += ((x1 - x0) ** 2 + (y1 - y0) ** 2) ** 0.5
```

路徑長對雜訊是**線性累積**的(不是 √n):每一幀的抖動都原封不動加進去,永遠
不會互相抵銷。模擬一個**完全靜止**的人(框高 200px,經 ROI EMA 平滑後):

| 框中心抖動 σ | 60 秒累積路徑 | 判定 |
|---|---|---|
| 0.5 px | 0.39 身高 | 等待 |
| 2.0 px | 1.54 身高 | 等待 |
| 3.0 px | 2.31 身高 | 等待 |
| **5.0 px** | **3.85 身高** | **徘徊** |

`wander_path` 預設 3.0,所以 σ≈5px 的抖動就足以讓一個站著不動的人被判成徘徊。
**再乘上等待閘門,這個人從頭到尾不會被做抽菸分析**——不是誤報,是靜默漏報。

更麻煩的是它**隨取樣率漂移**。同一個人、同一支攝影機、同樣的抖動(σ=3px),
只改 `sampling.target_fps`:

| target_fps | 累積路徑 | 判定 |
|---|---|---|
| 5 | 1.18 | 等待 |
| 10 | 2.31 | 等待 |
| **15** | **3.54** | **徘徊** |
| 20 | 4.75 | 徘徊 |
| 30 | 7.12 | 徘徊 |

`target_fps` 是**效能調校旋鈕**,不該改變語意判定。目前調快取樣率等於偷偷
把所有人推向「徘徊」。這條在論文裡是站不住的:同一段影片換個取樣率就換個
結論。

方向(未定):路徑改用位移門檻過濾(小於 k×σ 的逐幀位移不計)、或改用
時間正規化的估計量、或直接用 `span`(已經算好但目前沒參與判定)。

### 🔴 A2 `count_driven` 讓外觀網路對紅色警報完全沒有影響(已量化)

`pipeline.py:544`:

```python
if self.count_driven and allow and self.method.count_gate:
    cyc = 1.0
```

`allow` 為真時分數直接設成 1.0,**融合結果整個被丟掉**;`allow` 為假時
`allow_trigger=False`,再高的網路分數也觸發不了。兩條路都繞過網路,所以
`state_machine: 0.4 / network: 0.6` 這組權重在**紅色警報路徑上是死參數**。

實測(`demo_videos/抽菸_持續重複38秒.mp4`,警報時刻):

| | `rule` | `hybrid` |
|---|---|---|
| `count_driven: true`(**目前預設**) | 16.6s | **16.4s** |
| `count_driven: false` | 26.0s | 17.1s |

預設值下 `hybrid` 與 `rule` 差 0.2 秒,**實質上是同一個方法**;關掉才真的
分開(差 8.9 秒)。論文最重要的那張橫向比較表,目前會得出「加了外觀網路
沒有差別」——而原因是一個設定旗標,不是科學結論。

`count_driven` 本身是為了修「0.4×次數分上限 0.32 過不了 0.6 觸發線」而加的
(見 `inference_hmdb.yaml` 註解),動機正當,但副作用是把融合架空了。

### 🔴 A3 狀態機的分數從未被呼叫,S1→S2→S3 的順序檢查不參與判定(已確認)

`StageStateMachine` 每幀都 `push()`(`pipeline.py:423`、`:486`),但
**`score()` 在整個推論路徑裡一次都沒有被呼叫**——全庫只有 `tests/` 呼叫它。

實際進入融合的是 `HandToMouthCounter.score()`,也就是**次數警戒分數**。後果:

- S1→S2→S3 的**順序檢查完全沒作用**。只要 S2 停留夠久就計一次事件,手怎麼
  來的、怎麼走的都不看。這是本專案「動作序列」這個賣點的核心機制。
- `state_machine.window_sec`(8.0)與 `s2_min_dwell`(0.8)是**死參數**,
  調了不會有任何效果——而 `s2_min_dwell` 出現在方法參數表裡,使用者會以為
  調得動。
- 名為 `state_machine` 的融合權重,實際乘的是次數分數。這個命名會誤導讀者
  (也誤導了我)。

### 🟠 A4 `min_gap` 擋不住「同一口重複計數」(已量化)

結算時的間隔檢查用的是 `self._s2_last - self._last_event`
(`state_machine.py:146`)——**兩次停留的結束時間差**,裡面含了本次停留自己
的長度。所以實際要求的閒置間隔是 `min_gap − dwell`,對典型的 2~5 秒停留來說
是負的,等於沒有門檻。

實測(`min_gap=2.0`,停留 3.0 秒,手只放下 **0.7 秒**):

```
第 1 段 → 計入第 1 次
第 2 段 → 計入第 2 次
第 3 段 → 計入第 3 次
```

應該要用 `_s2_start - _last_event`。影響:手在臉附近反覆進出(搔癢、扶眼鏡
連續動作)會被計成多次獨立事件,直接推高次數、越過 `min_events`。

### 🟠 A5 左右手可能在同一條距離序列裡互換(推論,未重現)

`_wrist_nose_dist()` 回傳 `min(左腕距, 右腕距)`,**不記錄是哪一隻手**。而
S1/S3 的判定靠 `delta = past - d` 比較 0.6 秒前後的距離——如果期間較近的手
換了一隻,delta 比較的是**兩隻不同的手**,會憑空產生「快速靠近」或「快速
遠離」。

托腮(一手固定在臉附近)同時另一手抬起,正好構成這個情境。

### 🟠 A6 「0.6 秒前」其實是「6 個有效樣本前」(推論,未重現)

`self._hist` **只在量得到距離的幀才 append**(背向、太遠、鼻點不可信、腕點
不可見都會跳過),但 `lookback` 是**位置索引**:

```python
self.lookback = max(2, int(0.6 * fps))
past = self._hist[-1 - self.lookback]
```

棄權頻繁時(監控視角很常見),`past` 可能是好幾秒前的樣本,S1/S3 的「快速
變化」判定就失去時間基準。應該存 `(t, d)` 並依時間回查。

### 🟠 A7 再武裝門檻會系統性漏掉「手不放遠」的抽菸姿勢(先前已診斷)

S2 要被採信必須先「由遠而近」武裝:手得離臉 ≥ `near_ratio + rise_margin`
= 0.9 + 0.5 = **1.4 身體尺度**。這個機制是為了擋手被遮擋時的腕點幻覺,有效。

但代價是:手肘撐著、手在胸口與嘴之間小幅來回的抽菸姿勢,**手永遠不會退到
1.4 以外**,於是第一口之後就再也武裝不了,次數停在 1、永遠到不了
`min_events=2`。先前診斷 `alarm_track2_20260708_153431.mp4` 跳不出警報,
根因就是這個。

這是「防幻覺」與「容許小幅動作」的直接取捨,目前完全偏向前者。

### 🟡 A8 事件級評估用 temporal IoU 會低估長事件的召回(方法學)

`eval/event_eval.py` 以 **IoU-in-time ≥ 0.3** 判定命中。但警報區間是「觸發
到解除」,長度由 EMA 衰退決定(數十秒);真值區間是整段抽菸行為(可達數
分鐘)。一支 5 分鐘的抽菸真值配上 30 秒的正確警報,IoU = 0.1 < 0.3 →
**被算成漏測**。

警報系統的慣例是「真值區間內有沒有觸發」(point-in-interval),而不是區間
重疊率。照目前的算法,recall 會被系統性低估,而且**偵測得越果斷(警報越短)
分數越低**。

另外貪婪匹配(依 start 排序逐一取最佳)不是最佳指派,在事件密集時會低估
——影響比上一條小。

### 🟡 A9 README 對停留門檻的敘述前後不一

README §2 寫「S2 停留(**≥0.5 秒**,容忍 0.5 秒偵測中斷)結算為一次手到嘴
事件」,但 §3 與設定檔的 `min_dwell` 都是 **2.0 秒**(0.5 是
`gap_tolerance`,是中斷容忍不是停留門檻)。照 §2 讀會以為摸一下臉就計數。

### 🔴 P1-1 外觀網路的方法在多人畫面會當場崩潰(已重現)

`inference/pipeline.py:399` 只為**候選對象**(等待狀態)收 ROI:

```python
if self.use_model and self._is_smoking_candidate(st):
    model_tids.append(tid)
    rois.append(preprocess_roi(roi))
```

但後面三處都用 `tids`(**全部**追蹤對象)的位置去索引網路輸出:

```python
for i, tid in enumerate(tids):
    st.buffer.push(feats[i])          # :470
    cyc = ... float(net_scores[i])    # :504、:561、:567
```

`rois` 比 `tids` 短,索引就對不上。重現(兩個人,一個等待一個經過):

```
IndexError: index 1 is out of bounds for dimension 0 with size 1
```

即使沒炸(候選剛好是最後幾個),**特徵也會餵錯人**:甲的外觀特徵被推進乙
的時序緩衝,分數張冠李戴。這比崩潰更糟,因為它不會出聲。

影響 7 個方法裡的 3 個:`net`、`hybrid`、`hybrid+l1grammar`。預設的 `rule`

這是我加等待閘門(`57b8ee1`)時引進的回歸:當時只改了「誰要收 ROI」,沒改
「怎麼把結果配回去」。`model_tids` 收集了卻從未被使用,正是這件事做到一半
的痕跡。

### 🔴 P1-2 警報片段永遠分析不出標記(已重現)

主要的複查動線是「警報清單雙擊 → 先分析 → 看標記軸」。實測三支真實片段:

### 標記軸:指向第一次疑似抬手

播放器下方的紅點原本釘在**警報成立的那一刻**。但警報是「累積夠
`min_events` 次、且 P 持續超過門檻」的**結論**,成立時動作往往已經結束
十幾二十秒——點過去只會看到人站著,看不到想複查的那口菸。

改成釘在**第一次手到臉**上,包含太短而沒被計入的碰臉:確定是抽菸之後
回頭看,那些就是這輪行為的開頭。

實測 `demo_videos/抽菸_持續重複38秒.mp4`(`rule`,`inference_hmdb.yaml`):

```
疑似時刻  4.4 / 5.6 / 10.8 / 15.0 / 20.2 / 24.5
觸發 26.1s → 標記 4.4s     (提前 21.7 秒)
分析路徑  觸發 36.0s → 標記 10.9s
```

途中踩到兩個坑,都值得記著:

- **錨在 S1 階段上根本抓不到**。S1 只在一個很窄的距離帶內才回報
  (`inference/skeleton.py:190`,`near_eff < d < near_eff + 2×move` 且距離

  標記一路走的是「沒看到抬手」的退路值,**看起來剛好像有在動作**,所以
  沒有立刻發現。改用事件結算時回填的「結束 − 停留」當錨點:事件一定有。
- **改了語意卻沒讓快取失效**。`.analysis/*.npz` 側車檔照載,重開影片看到
  的還是上一版的標記,而且畫面上沒有任何跡象說它沒重跑。`CACHE_VERSION`
  現在 = 3,並補了 `TestCacheVersion` 三項回歸測試釘住這件事。

順帶把警報片段的前置緩衝改成可調(`alarm.clip_pre_sec`,5–30 秒,預設
10)。現在提前量常有 20 秒以上,預設值拍不到動作開頭——診斷框會明講,
不會讓人誤以為是漏偵測。播放器不受此限,整支檔案都在。

### 只有「等待」才做抽菸分析

`presence.smoking_requires_waiting`(預設開)。經過與徘徊的人**連分析都
不做**——不裁 ROI、不跑外觀網路、不推狀態機、不累積次數。

第一版做成「分析照跑,最後才擋掉警報」,一點算力都沒省,與這條規則的
目的相反。改成真的跳過之後(單步中位):

| 方法 | 閘門關 | 閘門開 |
|---|---|---|
| `hybrid` | 43.3 ms | **19.6 ms**(2.2 倍) |
| `rule` | — | 20.3 ms |

純規則省得有限是結構性的:成本 93% 在 YOLOv8-pose,姿態偵測是整張影格
一次、與人數無關,而且不先偵測就不知道誰在等待。

⚠ 「等待」要在場滿 `long_stay` 秒(預設 20)才成立,所以**十幾秒的警報
片段永遠到不了等待**,拿它回頭重跑重現不出這個狀態。

### 警報成立卻沒有片段(兩個獨立的 bug)

- **背景執行緒呼叫 `root.after`**：Tkinter 的任何 API 都只能在主執行緒
  用,三個呼叫點把工作執行緒靜靜弄死——沒有片段,也沒有影格。
- **來源在後錄 4 秒內結束**：`_active_recs` 沒有被收尾,警報跳了、ID 也
  顯示了,片段卻被丟掉。

### GUI 收斂

- 主畫面只留四個開關(徘徊警報 / 等待警報 / 抽菸警報 / 開啟骨架可視化),
  警報清單只顯示片段名稱與縮圖,過程訊息全部移到獨立的診斷框——警報要
  一眼看得出「有幾件」,混進 log 就看不出來了。
- 選方法時跳出**該方法自己的**參數表(`ui/settings_dialog.py`),各方法
  各記各的覆寫值:論文要橫向比較,調鬆 `rule` 不該連帶改到 `hybrid`。
- 補回移動排除開關——先前拿掉主畫面的勾選框卻沒放進參數表,行為沒變但
  使用者失去了唯一的開關,看起來就像規則壞掉。

### 播放器改成標記工具

- **先分析後播放**:點開影片先跑一次判定,標記出來才開始播。結果存成
  側車檔(`.analysis/<檔名>.npz`),**原始影片完全不動**,同一支第二次開
  是秒開(17s → 0.46s)。對話框給三條出口:等它跑完 / 先播放(分析丟到
  背景)/ 不分析。
- **可點選的標記軸**、逐幀、變速、截圖、快捷鍵、循環、全螢幕;無音訊。
- 骨架疊加改吃分析時的快取,不再播放時每幀重跑偵測。
- 分析的姿態偵測改成批次:**2.7 倍加速**。
- 修正播放速度比實際慢(0.68–0.80x):補回解碼與繪圖的時間;60fps 來源
  改用丟幀保同步。
