## 未修正的演算法問題(2026-08-16 稽核)

上一輪查的是工程缺陷,這一輪查**判定邏輯本身**。標「已量化」的附了可重跑的
數字,標「推論」的只由程式碼推得。這些多半不是「壞掉」,而是**方法上站不住
腳**——論文寫下去會被問的那種。同樣尚未動手修。

### 🔴 A1 累積路徑把偵測抖動當成移動,靜止的人會被判成徘徊(已量化)

`PresenceClassifier._metrics()` 用**逐幀位移的總和**當「走了多少」:

```python
for (_, x0, y0, _), (_, x1, y1, _) in zip(pts, pts[1:]):
    path += ((x1 - x0) ** 2 + (y1 - y0) ** 2) ** 0.5
```

路徑長對雜訊是**線性累積**的(不是 √n):每一幀的抖動都原封不動加進去,永遠
不會互相抵銷。模擬一個**完全靜止**的人(框高 200px,經 ROI EMA 平滑後):

| 框中心抖動 σ | 60 秒累積路徑 | 判定 |
|---|---|---|
| 0.5 px | 0.39 身高 | 等待 |
| 2.0 px | 1.54 身高 | 等待 |
| 3.0 px | 2.31 身高 | 等待 |
| **5.0 px** | **3.85 身高** | **徘徊** |

`wander_path` 預設 3.0,所以 σ≈5px 的抖動就足以讓一個站著不動的人被判成徘徊。
**再乘上等待閘門,這個人從頭到尾不會被做抽菸分析**——不是誤報,是靜默漏報。

更麻煩的是它**隨取樣率漂移**。同一個人、同一支攝影機、同樣的抖動(σ=3px),
只改 `sampling.target_fps`:

| target_fps | 累積路徑 | 判定 |
|---|---|---|
| 5 | 1.18 | 等待 |
| 10 | 2.31 | 等待 |
| **15** | **3.54** | **徘徊** |
| 20 | 4.75 | 徘徊 |
| 30 | 7.12 | 徘徊 |

`target_fps` 是**效能調校旋鈕**,不該改變語意判定。目前調快取樣率等於偷偷
把所有人推向「徘徊」。這條在論文裡是站不住的:同一段影片換個取樣率就換個
結論。

方向(未定):路徑改用位移門檻過濾(小於 k×σ 的逐幀位移不計)、或改用
時間正規化的估計量、或直接用 `span`(已經算好但目前沒參與判定)。

### 🔴 A2 `count_driven` 讓外觀網路對紅色警報完全沒有影響(已量化)

`pipeline.py:544`:

```python
if self.count_driven and allow and self.method.count_gate:
    cyc = 1.0
```

`allow` 為真時分數直接設成 1.0,**融合結果整個被丟掉**;`allow` 為假時
`allow_trigger=False`,再高的網路分數也觸發不了。兩條路都繞過網路,所以
`state_machine: 0.4 / network: 0.6` 這組權重在**紅色警報路徑上是死參數**。

實測(`demo_videos/抽菸_持續重複38秒.mp4`,警報時刻):

| | `rule` | `hybrid` |
|---|---|---|
| `count_driven: true`(**目前預設**) | 16.6s | **16.4s** |
| `count_driven: false` | 26.0s | 17.1s |

預設值下 `hybrid` 與 `rule` 差 0.2 秒,**實質上是同一個方法**;關掉才真的
分開(差 8.9 秒)。論文最重要的那張橫向比較表,目前會得出「加了外觀網路
沒有差別」——而原因是一個設定旗標,不是科學結論。

`count_driven` 本身是為了修「0.4×次數分上限 0.32 過不了 0.6 觸發線」而加的
(見 `inference_hmdb.yaml` 註解),動機正當,但副作用是把融合架空了。

### 🔴 A3 狀態機的分數從未被呼叫,S1→S2→S3 的順序檢查不參與判定(已確認)

`StageStateMachine` 每幀都 `push()`(`pipeline.py:423`、`:486`),但
**`score()` 在整個推論路徑裡一次都沒有被呼叫**——全庫只有 `tests/` 呼叫它。

實際進入融合的是 `HandToMouthCounter.score()`,也就是**次數警戒分數**。後果:

- S1→S2→S3 的**順序檢查完全沒作用**。只要 S2 停留夠久就計一次事件,手怎麼
  來的、怎麼走的都不看。這是本專案「動作序列」這個賣點的核心機制。
- `state_machine.window_sec`(8.0)與 `s2_min_dwell`(0.8)是**死參數**,
  調了不會有任何效果——而 `s2_min_dwell` 出現在方法參數表裡,使用者會以為
  調得動。
- 名為 `state_machine` 的融合權重,實際乘的是次數分數。這個命名會誤導讀者
  (也誤導了我)。

### 🟠 A4 `min_gap` 擋不住「同一口重複計數」(已量化)

結算時的間隔檢查用的是 `self._s2_last - self._last_event`
(`state_machine.py:146`)——**兩次停留的結束時間差**,裡面含了本次停留自己
的長度。所以實際要求的閒置間隔是 `min_gap − dwell`,對典型的 2~5 秒停留來說
是負的,等於沒有門檻。

實測(`min_gap=2.0`,停留 3.0 秒,手只放下 **0.7 秒**):

```
第 1 段 → 計入第 1 次
第 2 段 → 計入第 2 次
第 3 段 → 計入第 3 次
```

應該要用 `_s2_start - _last_event`。影響:手在臉附近反覆進出(搔癢、扶眼鏡
連續動作)會被計成多次獨立事件,直接推高次數、越過 `min_events`。

### 🟠 A5 左右手可能在同一條距離序列裡互換(推論,未重現)

`_wrist_nose_dist()` 回傳 `min(左腕距, 右腕距)`,**不記錄是哪一隻手**。而
S1/S3 的判定靠 `delta = past - d` 比較 0.6 秒前後的距離——如果期間較近的手
換了一隻,delta 比較的是**兩隻不同的手**,會憑空產生「快速靠近」或「快速
遠離」。

托腮(一手固定在臉附近)同時另一手抬起,正好構成這個情境。

### 🟠 A6 「0.6 秒前」其實是「6 個有效樣本前」(推論,未重現)

`self._hist` **只在量得到距離的幀才 append**(背向、太遠、鼻點不可信、腕點
不可見都會跳過),但 `lookback` 是**位置索引**:

```python
self.lookback = max(2, int(0.6 * fps))
past = self._hist[-1 - self.lookback]
```

棄權頻繁時(監控視角很常見),`past` 可能是好幾秒前的樣本,S1/S3 的「快速
變化」判定就失去時間基準。應該存 `(t, d)` 並依時間回查。

### 🟠 A7 再武裝門檻會系統性漏掉「手不放遠」的抽菸姿勢(先前已診斷)

S2 要被採信必須先「由遠而近」武裝:手得離臉 ≥ `near_ratio + rise_margin`
= 0.9 + 0.5 = **1.4 身體尺度**。這個機制是為了擋手被遮擋時的腕點幻覺,有效。

但代價是:手肘撐著、手在胸口與嘴之間小幅來回的抽菸姿勢,**手永遠不會退到
1.4 以外**,於是第一口之後就再也武裝不了,次數停在 1、永遠到不了
`min_events=2`。先前診斷 `alarm_track2_20260708_153431.mp4` 跳不出警報,
根因就是這個。

這是「防幻覺」與「容許小幅動作」的直接取捨,目前完全偏向前者。

### 🟡 A8 事件級評估用 temporal IoU 會低估長事件的召回(方法學)

`eval/event_eval.py` 以 **IoU-in-time ≥ 0.3** 判定命中。但警報區間是「觸發
到解除」,長度由 EMA 衰退決定(數十秒);真值區間是整段抽菸行為(可達數
分鐘)。一支 5 分鐘的抽菸真值配上 30 秒的正確警報,IoU = 0.1 < 0.3 →
**被算成漏測**。

警報系統的慣例是「真值區間內有沒有觸發」(point-in-interval),而不是區間
重疊率。照目前的算法,recall 會被系統性低估,而且**偵測得越果斷(警報越短)
分數越低**。

另外貪婪匹配(依 start 排序逐一取最佳)不是最佳指派,在事件密集時會低估
——影響比上一條小。

### 🟡 A9 README 對停留門檻的敘述前後不一

README §2 寫「S2 停留(**≥0.5 秒**,容忍 0.5 秒偵測中斷)結算為一次手到嘴
事件」,但 §3 與設定檔的 `min_dwell` 都是 **2.0 秒**(0.5 是
`gap_tolerance`,是中斷容忍不是停留門檻)。照 §2 讀會以為摸一下臉就計數。

### 🔴 P1-2 警報片段永遠分析不出標記(已重現)

主要的複查動線是「警報清單雙擊 → 先分析 → 看標記軸」。實測三支真實片段:

注意調大 `clip_pre_sec` 救不了——在場時間是從片段的第一幀重算的,不是原始

## 2026-08-19 融合權重改名:讓名字說實話(清理 StageStateMachine 的第 1 步)

**問題:**融合權重放在 `state_machine.weights` 底下、第一項叫「規則權重」,
讓人以為調的是 StageStateMachine 的順序檢查分數。**不是。**
`cycle_score()` 的第一個參數一直都是 `HandToMouthCounter.score()`(次數警戒),
而 StageStateMachine 的 `score()` 根本沒有人讀。

**改了什麼(純改名,行為零變化):**

| 舊 | 新 |
|---|---|

| `state_machine.weights.network` | `fusion.network` |
| GUI 滑桿「規則權重」 | 「次數權重」 |
| `cycle_score(sm_score, net_score, w_sm, w_net)` | `cycle_score(count_score, net_score, w_count, w_net)` |

搬成獨立的 `fusion:` 區塊而不是只改內層鍵名:這樣還活著的東西(融合權重)

## 2026-08-19 rule+order:把狀態機沒接上線的那半條規則補回來

**發現:**`StageStateMachine` 每幀都被 `push()`,但 `score()` 在 pipeline
與 GUI 裡**從來沒有被呼叫過**(只有測試在用)。連帶 `configs/inference.yaml`
的 `state_machine.window_sec` 與 `s2_min_dwell` 目前不影響任何行為,
GUI 標成「規則權重」的滑桿實際上乘的是 `HandToMouthCounter` 的分數。

**它本來要守的兩件事,現況只守了一半:**

- **S1 要在 S2 之前** —— 已由 `SkeletonStageEstimator` 的 armed 機制守住
  (手要先離臉 ≥ near+0.5 才採信 S2),只是實作在別的地方
- **S3 要在 S2 之後** —— **沒有人在守**。`HandToMouthCounter` 結算 S2 段落
  的條件是「任何非 S2 階段持續超過 gap_tolerance」,包含背景與棄權,
  所以「手到嘴然後手就看不見了」跟「手到嘴再放下」被當成同一件事

**做了什麼:**`HandToMouthCounter` 新增 `require_release` / `release_window`,
掛成方法清單的 `rule+order`(`Method.require_release`,由 `apply()` 注入設定)。
`scripts/compare_rule_variants.py` 可重跑比較。

**實測(64 段警報片段重播,事件層級):**

一個「事件」= 一次手停在臉部 2–5 秒的停留。累積 3 次才會變成紅色警報。

| 片段標籤 | rule 計入 | rule+order 計入 | 被擋掉 |
|---|---|---|---|
| desk_work(桌面工作,誤報) | 1 | 0 | 1 |
| other_neg(其他非抽菸,誤報) | 4 | 3 | 1 |
| smoking(真的抽菸) | 4 | 4 | **0** |
| **合計** | **9** | **7** | **2** |

**擋掉 2 個誤報事件、真事件一個都沒動。** 方向正確,但 9 個事件的樣本量
下不了結論,所以 `rule` 仍是預設。

**release_window 2.0 秒是量出來的,不是猜的。** 一開始設 1.0 秒,
結果誤殺了一段真的抽菸(`alarm_track2_20260708_153431`):

```
3.0s – 5.0s  S2 手在嘴（2 秒,真的一口）
5.2s – 7.0s  背景/看不到（手離嘴後垂下去,骨架看不到手）
7.1s – 7.6s  S3 放下      ← 隔了 2.1 秒才判得出來
```

手離開嘴之後常常先「看不到」一兩秒才重新被看到往外拉。掃過
1.0 / 1.5 / 2.0 / 2.5 / 3.0 / 4.0 秒:2.0 秒開始真事件全保住,之後飽和。

**⚠ 警報層級無法驗證:**警報要求 90 秒視窗內 ≥ 3 次事件,而 `alarms/clips`
的片段中位數只有 **13.6 秒**(最長 14.1 秒)——視窗根本放不下,重播出來
每段最多 2 個事件,任何規則變體都不會觸發警報。要比警報層級的精確率/
召回率,只能重錄連續影像。

**實作上踩到的坑(已寫成測試):**
- pending 的解算**必須放在結算區塊之後**。S3 常常正好落在結算的那一幀
  (結算等 gap_tolerance 0.5 秒,estimator 判 S3 要跟 0.6 秒前比較),
  放在前面的話這一幀的 S3 會被自己剛建立的 pending 錯過。修正前後
  被擋掉的事件從 6 個降到 4 個,抽菸從 2 個降到 1 個
- 事件時間戳要用「停留結束」而不是「確認放下」,否則 `min_gap` 與 90 秒
  滾動視窗會被 `release_window` 拖著跑
- `release_window` 必須大於 `gap_tolerance`,不然所有事件都會被擋掉,
  而且不會有任何錯誤訊息

## 2026-08-18 單幀對照組(control group)

**做了什麼:**`stage2/frame_baseline.py` + `stage2/train_frame.py`。只看
「手舉起來」的單幀骨架判動作,段級以 top-k 平均聚合。實作兩種架構
(運動學 MLP / 單幀骨架圖),但**只有 gcn 掛進 `inference/methods.py`**
成為 `rule+frame_gcn` 一格 —— gcn 就是 L1 的 ST-GCN 拿掉時間卷積,與
`rule+l1grammar` 只差一個變因;mlp 換的是一整組手工特徵,掛上去會讓
「單幀 vs 時序」的差距說不清楚從哪來,所以留在離線比較
(`train_frame.py --arch mlp`)。設計與結果見
[`單幀對照組.md`](單幀對照組.md)。

**為什麼:**主線假設「抽菸與其他手到嘴動作的差別在時間軸上」,但這件事
從來沒有被量過。單幀就能拿到一樣的分數的話,兩層時序架構是白做的。

**實測到什麼 —— 結論被切法翻過來,這才是重點:**

分層隨機 k-fold(與 train_l2 同一組 fold)看起來單幀完勝:

| 方法 | 抽菸 AUC |
|---|---|
| 單幀 MLP | 0.891 |
| 單幀 GCN | 0.802 |
| 片段文法 | 0.733 |
| L1 + 片段文法 | 0.750 |

但同一次執行的**捷徑探針**(只餵軀幹傾斜/遠近/朝向這 7 維、完全不看手臂)
拿到 **AUC 0.94**。抽菸正樣本只有兩個錄影場次(20260708 五段、20260709 一段),
負樣本散在六個場次;分層隨機切法會把同一場錄影的段同時放進訓練與驗證,
模型記住機位就能得分。

加了 `--split session`(一個錄影場次 = 一折,訓練與驗證不共用機位)之後:

| 方法 | 分層隨機 | 依場次 | 變化 |
|---|---|---|---|
| 單幀 MLP | 0.891 | **0.609** | −0.282 |
| 單幀 GCN | 0.802 | **0.661** | −0.141 |
| 捷徑探針 | 0.943 | 0.652 | −0.291 |
| 片段文法 | 0.733 | 0.733 | 0 |
| L1 + 片段文法 | 0.750 | 0.750 | 0 |

- 兩個單幀對照組都崩了,掉幅與探針同一個量級 —— 原本的優勢是記憶機位
- 時序那兩條**完全沒動**:片段文法沒有可學參數,學不到場景也就沒得崩
- 跨場次驗證下時序勝出 0.089 ~ 0.141,原本的假設(差別在時間軸上)站得住

其他改動:全域特徵改為預設關閉(開了分層隨機下 MLP 會從 0.891 跳到 0.968,
那 0.077 全是捷徑);捷徑探針每次訓練都會跑;分層隨機 + 探針偏高時腳本會
拒絕下結論,直接叫人改跑 `--split session`。

**仍然存在的限制:**抽菸正樣本 6 段、兩個場次,其中一個場次只有 1 段
(驗證 20260708 那一折,訓練集只剩 1 段正樣本)。依場次切之後探針仍有 0.65。
治本是補跨場景正樣本,與 L2 訓不動是同一個瓶頸。

**外觀對照組(YOLO26-cls)被資料擋住:**`stage2/export_crops.py` 已寫好,
但實測 `alarms/clips` 每一段(含最新的 08-16)都把人物框 / 骨架 / 腕-鼻線
畫進畫面才存檔。紅線只在規則判定成立時才畫 —— 外觀模型會直接學「有沒有
紅線」,那是上一版規則的答案不是抽菸。腳本加了疊加層守門(飽和純色像素
佔比,實測 0.47% vs 門檻 0.2%),預設拒絕匯出。要做這一組得先把 GUI 的
