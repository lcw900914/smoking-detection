## 1. 系統在做什麼

不依賴香菸物件、**純動作時序分析**的抽菸行為偵測。監控距離下香菸只有
幾個像素,所以不偵測「菸」,而是偵測「抽菸這個動作序列」:
舉手靠近嘴 → 停留吸食 → 放下 → 週期性重複。

開發環境:單張 RTX 2060(6GB VRAM),Python 3.13 + PyTorch 2.12 + CUDA 12.6。
第一階段架構全程只用 2D 算子,保留向邊緣 NPU 移植的相容性。

系統分兩階段:

```
第一階段(即時,線上)          第二階段(離線,驗證)
YOLOv8-pose + ByteTrack   →   兩層骨架時序模型
外觀網路 + 幾何規則 + 計數器      L1 基元 → L2 組合
高召回,圈出候選               過濾誤報,降級不否決
```

**降級不否決**是核心原則:第二階段判「非抽菸」只把警報降為橘色
「待人工複查」,絕不取消。召回由結構保證不會下降。

兩階段的各種組合(要不要外觀網路、要不要複核、複核用文法還是學習版)
做成**可切換的方法**,由同一支 GUI 的下拉選單選——見第 3.5 節。

## 3. 第二階段:兩層骨架時序模型(2026-08 現行架構)

完整設計見 `docs/兩層骨架時序模型設計.md`。這裡只給接手需要的最小理解。

```
節點序列 (T,17,3)
   ├─→ 拓樸圖特徵 (T,13,5)   平移+尺度正規化,不旋轉
   └─→ 運動學特徵 (T,45)     身體座標系裡的角度與距離,旋轉不變
         ▼  L1 PrimitiveNet(ST-GCN + 運動學支流,100,520 參數)
   逐幀基元:靜置 / 舉手 / 停留臉部 / 放下 / 其他活動        ← 淺層
         ▼  分段(每片段帶 21 維屬性)
   片段序列:[舉手 0.4s] [停留 1.8s, 腕鼻距 0.48] [放下 0.7s] …
         ▼  L2 CompositionNet(時間感知 Transformer,21,238 參數)
   具體動作:抽菸 / 喝水 / 講電話 / 扶眼鏡 / 抓頭髮 / 其他    ← 深層
```

**為什麼分兩層**:L1 的監督訊號由規則自動產生(17,338 筆逐幀標籤,
**不需要人標**),再多錄影片就自動變多;L2 的輸入被壓成十幾個 token,
參數量壓到 2 萬,才有機會用幾十段片段學起來。誤判時也看得出是哪一層錯。

**輸出長這樣**(`HierarchicalRecognizer.explain()`,可直接給人看):

```
【淺層基元時間軸】
    2.7s 左手 舉手(0.4s, 腕鼻距 0.78)
    3.1s 左手 停留臉部(1.8s, 腕鼻距 0.48)
    5.2s 左手 停留臉部(1.8s, 腕鼻距 0.48)
    7.0s 左手 放下(0.7s, 腕鼻距 1.11)
    …
【節律統計】
  停留 4 次、完整循環 4 次、單次平均 1.8s、間隔變異 0.87、最小腕鼻距 0.36
【深層判定】
  抽菸  0.87    其他  0.13
```

## 3.5 方法可切換(2026-08-13)—— 動手前務必先讀這一節

**這個專案只有一支 GUI。所有抽菸判定方法都必須是那支 GUI 下拉選單裡的
一個選項。** 這是使用者明確的要求,理由是論文最後要在完全相同的輸入與
操作條件下橫向比較各方法的效果——方法散在不同入口、不同腳本,就沒辦法
公平比較,也沒辦法現場 demo 差異。

登錄表在 `inference/methods.py`。**新增一種方法時,唯一要改的地方就是在
`METHODS` 補一個 `Method`**;GUI 選單、`--method` 參數、可用性檢查(缺哪個
權重檔)全部自動跟上。**不要**在 GUI 或管線裡寫 `if method == ...`。

一個「方法」= 一條完整的端到端判定路徑,由兩段組成:

| stage1(即時) | stage2(候選複核,離線) |
|---|---|
| `rule` 骨架幾何 + 狀態機 | `None` 不複核 |
| `network` 外觀 CNN 時序 | `grammar` 片段文法(零學習權重) |
| `hybrid` 兩者加權融合 | `l1+grammar` L1 網路基元 + 文法 |
| | `l1+l2` L1 + 學習版 L2 |

目前 7 種:`rule`(預設)、`rule+grammar`、`rule+l1grammar`、`rule+l1l2`、
`net`、`hybrid`、`hybrid+l1grammar`。`python -m inference.pipeline --method list`
會印出全部方法與各自缺少的權重。

**「純規則」的界線**:指**判定規則**不含學習權重。人物框與關鍵點仍然來自
YOLO——那一段是感測器(把畫面變成座標),不是在決定「這是不是抽菸」。
`Method.ai_free_decision` 就是在標這件事,論文分組時直接用它。

### 第二階段已經接進管線了(原 P2-1)

`inference/verifier.py` + 管線裡的節點滾動緩衝(`TrackState.pose_hist`,
預設 90 秒,17×3 float @10fps 每人每分鐘約 120 KB,成本近零,**恆常累積**)。
紅色警報一觸發就把該對象**過去** 90 秒的序列丟給背景執行緒複核。

> 取過去而不等未來:紅色警報要 ≥3 次手到嘴事件加 sustain 秒才成立,
> 證據早就落在過去了。等未來幾秒只會延後結果,換不到新資訊。

複核結果三態,對應三種不同的事實:

| 狀態 | 意思 | 對警報的影響 |
|---|---|---|
| `confirmed` 已確認 | 複核也認為是抽菸 | 維持紅色 |
| `review` 待複查 | 複核認為是別的動作 | **降為橘色**,警報仍在 |
| `abstain` 無法複核 | 骨架看不到手,沒有足以判斷的輸入 | 維持紅色 |

`abstain` 不是湊出來的第三態,是必要的:47% 的片段鼻點可信幀不到 20%。
若這種情況也降級,等於因為攝影機角度不好就把真警報壓掉——那正是這個模組
被明令禁止做的事。降級門檻也刻意比升級寬(`min_smoking = 0.25`):誤降
一次真警報的代價遠高於多留一個橘色待複查。

這條紅線寫成純函式 `verifier.decide()` 並單獨測試(`tests/test_methods.py`
的 `TestDecide`),不是只靠註解。**改那個函式前先確認理由已不成立。**

## 4. 目前的效能數字(全部誠實,不修飾)

### 第一階段(HMDB51 驗證集 105 段)

clip accuracy 93.3%、macro-F1 0.86、AUC 0.85、smoking recall 11/18。

**但實地(監控俯視角)不漏測而誤測偏多。** 2026-07-13 把 57 段警報特寫
逐一檢視,**幾乎全為誤報**(約 60% 桌面工作/托腮、15% 抱胸/插腰、
15% 喝水類)。根因:HMDB51 是電影片段、多為正面近景,與監控俯視角有
嚴重 domain gap;實測背向辦公人員的網路分數常達 0.7–0.95(訓練集裡
沒有這類負樣本)。

### 第二階段 L1 淺層(5-fold,64 段,規則有把握的幀上)

| 基元 | 召回 |
|---|---|
| 靜置 | 0.86 |
| 舉手 | 0.82 |
| 停留臉部 | 0.90 |
| 放下 | 0.83 |
| 其他活動 | 0.52 |
| **整體** | **0.707 ± 0.018** |

四個有語意的基元都在 0.82–0.90;整體被概括類「其他活動」拉低,
那一類本來就沒有一致的樣貌。

### 第二階段深層(抽菸維度 AUC,64 段,正樣本 6 段)

| 淺層 | 深層 | AUC |
|---|---|---|
| 規則 | 片段文法 | 0.733 |
| **L1 網路** | **片段文法** | **0.750 ← 目前最佳,也是預設路徑** |
| L1 網路 | 學習版 L2 | 0.580 |

**學習版 L2 輸給無參數的文法。** 原因不是架構,是 6 段正樣本學不動
2 萬個參數。所以:

> ⚠️ **推論時不要載入 `checkpoints/hier_l2.pt`。**
> `HierarchicalRecognizer` 不給 `l2_ckpt` 就會自動走文法,那目前比較準。
> `train_l2.py` 每次跑完會自己跟文法比一次並印出該用哪個。

## 6. 後續計畫

按**依賴關係**排序,不是按難度。前面沒做,後面做了也沒用。

### P0 —— 解除資料瓶頸(不做這兩項,其餘全部白費)

**P0-1. 改善姿態可見度**

- 問題:47% 的片段骨架不可用,主因是俯視角 + 背向(第一階段實測 78% 背向)
- 做法(擇一或並行):
  - 調整鏡位:降低俯角、改側向架設
  - 換更強的姿態模型(現用 `yolov8s-pose.pt`,可試 yolov8m/l-pose 或
    RTMPose——第二階段離線執行,不受邊緣算力限制)
  - 對背向情況明確棄權(`inference/skeleton.py:estimate_orientation`
    已有閘門,可延伸到第二階段的資料篩選)
- 驗收:重新回抽後,「鼻點可信幀 < 20%」的片段比例從 47% 降到 20% 以下

**P0-2. 錄製抽菸正樣本(唯一硬門檻,從 2026-07 掛到現在)**

- 規格:場域擺拍,5–8 人 × 站/坐 × 多角度,每段 **2–3 分鐘完整過程含點菸**
  (不是十幾秒的片段——節律要放得進去)
- 目標量:30–50 段可用正樣本(現在是 4 段)
- **用 GUI 錄**(`啟動GUI.bat`),不要用命令列管線:GUI 在警報錄影的當下
  會同步把該對象的節點序列寫成 `annotations/pose/*.npz`
  (`scripts/gui.py:_write_pose`),格式與 `extract_pose.py` 完全一致。
  「錄影疊加」開關**保持預設關閉**——關 = 存乾淨原始影格,之後做外觀
  分支才有得用;烙印上去就救不回來了
- 注意現有錄製是「前 10 秒 + 後 4 秒」約 14 秒,**放不下一根菸的節律**。
  要 2–3 分鐘的完整過程,得先做 P2-2 的長緩衝,或先用外部錄影
  再走 `extract_pose.py` 回抽(但回抽依賴畫面上的紅框定位,
  與乾淨影像互斥——兩者擇一)
- 驗收:`python -m stage2.train_l2 --l1 checkpoints/hier_l1.pt` 印出
  「✓ 學習版勝過文法基線」

### P1 —— 讓深層真的學得起來

**P1-1. 用新細類複標既有 58 段粗類負樣本**

```bash
python scripts/label_tool.py          # 1-8 動作,9/0/- 排除
```
`other_neg` / `desk_work` 會被標示「舊類別,建議複標」。裡面混著扶眼鏡與
抓頭髮,做六分類前一定要拆開。進度列直接顯示六個深層類別各有幾段。

**P1-2. 訓練 L2 六分類並取代文法**

```bash
python -m stage2.train_l1                                  # 淺層(隨時可重跑)
python -m stage2.train_l2 --l1 checkpoints/hier_l1.pt      # 深層
```
主指標不是 accuracy,是**固定 100% 抽菸召回下的誤報過濾率**
(`train_l2.py:filter_rate_at_full_recall`)——第二階段是過濾器不是分類器。

### P2 —— 上線與長時窗

**P2-1. 把兩層模型接進管線 —— ✅ 2026-08-13 已完成(見第 3.5 節)**

`inference/verifier.py` + 管線的 90 秒節點滾動緩衝 + 背景執行緒複核 +
GUI 顯示「複核中 → 已確認(紅)/ 待複查(橘)/ 無法複核(紅)」,
記錄裡雙擊該列會跳出 `explain()` 的基元時間軸與節律統計。

剩下的小尾巴(不阻擋任何事):

- GUI 自己那份 `pose_buffer`(100 幀 ≈ 10 秒)還在,只服務錄影當下落地
  npz(`_write_pose`)。它與管線的 90 秒緩衝**目的不同**,兩份都要留:
  一份是訓練資料的來源,一份是複核的輸入
- 複核目前一個 track 一次警報只做一次;警報持續中不重複複核

**P2-2. 長時窗節律(仍未解 —— 卡在資料,不是程式)**

管線的緩衝已經是 90 秒,但**訓練用的片段只有 13 秒**,所以節律統計
(間隔變異係數那些)在訓練時仍然學不到東西。要等 P0-2 補錄 2–3 分鐘的
完整過程,才輪得到把 L2 的訓練視窗拉長、把節律項的權重調高。

也就是說:**現在把複核視窗開到 90 秒,只有「推論時看得比較遠」的好處,
文法的判準本身還是為 13 秒的片段調的。** 別誤以為長時窗已經生效。

## 8. 已知地雷(踩過了,不要再踩)

這一節是整份文件最重要的部分。以下每一條都是實際debug出來的,
多數已經寫成測試,**改程式前先看有沒有踩到**。

### 資料與特徵

1. **缺值不能填 0。** 鼻點不可信時腕-鼻距離會被清成 0,拿去取 min 會得到
   「腕鼻距 0.00」——那是最強的抽菸證據。缺值一律填 `FAR = 3.0`(手離臉
   很遠),另用 `A_FACE_RATIO` 記錄「到底量到沒有」。
   (`stage2/primitives.py`)

2. **「幾何有效」與「臉部可用」必須分開。** 綁在一起會出事:俯視角有 66%
   的幀鼻點不可信,若一併棄權,連「手放在腿上沒動」這種確定的事實都標
   不出來。分開後逐幀標籤覆蓋率從 30% 提到 48%。
   (`K_VALID` vs `K_FACE_OK`)

3. **速度要先平滑再差分。** 關鍵點逐幀抖動 2–4 px,直接差分算出來的腕速
   中位數是 1.15 身體尺度/秒——比真實手部移動還大,「靜止」這個概念會
   直接消失。平滑後降到 0.64。也因此 `STILL_SPEED = 0.8` 看起來偏大是
   對的,那是量測速度不是物理速度。

4. **腕點幻覺。** 手背在身後時,姿態模型會以 0.9 的置信度把腕點畫在衣領
   上,腕-鼻距離剛好落在門檻內。**置信度門檻擋不住。** 解法是「武裝」
   機制:停留要採信,前面得先看到手離臉夠遠(幻覺點恆定懸停,永遠不會
   先遠離再靠近)。

5. **模型分數對縮放/重編碼敏感。** demo 影片必須原生尺寸 + 近無損編碼
   (x264 crf12),重壓過的素材分數會歪。

6. **警報片段有疊加烙印,不能拿來訓練外觀模型**(標註洩漏)。
   GUI 已有「乾淨影像」開關,錄製時要打開。

### 模型與訓練

7. **沒量到 ≠ 有。** L1 會在鼻點整段不可信的地方也預測「停留臉部」
   (它從手臂幾何推的)。那是合理預測但不是證據,`find_cycles()` 會跳過。
   計入等於把「不知道」當成「有」。

8. **沒有輸入就不該有輸出。** L1 對每一幀都會給答案,包括腕點根本偵測
   不到的幀。實測有片段 96% 的幀量不到手腕卻被切出六段「停留臉部」。
   `analyze()` 走 L1 路徑時會把 `K_VALID = 0` 的幀退回棄權。
   **注意只遮這一種**——鼻點不可信、門檻模糊帶那兩種棄權不遮,那裡手臂
   幾何是在的,由網路補上正是 L1 存在的理由。

9. **L1 是欠擬合不是過擬合。** 30 epoch val 0.589、100 epoch val 0.738,
   而且 train 0.737 ≈ val 0.738。看到分數低不要急著加正規化,先給訓練時間。

10. **推論常常 batch=1,不要在小模型裡用 BatchNorm 吃手工統計量。**
    train/eval 行為差異是小資料專案最常見的翻車點。L2 的 16 維節律統計
    改用固定常數標準化(`composition.normalize_stats`)。

11. **模糊帶標籤要 ignore,不要硬給。** 規則偽標籤在門檻附近一律標 −1
    不進損失。寧可少教,不要教錯。

12. **多條件合取用幾何平均,不要連乘。** 連乘會讓條件多的類別天生吃虧:
    抽菸五條判準、抓頭髮兩條,同樣每條 0.8,連乘是 0.33 對 0.64,
    抓頭髮永遠贏。(`composition._fuzzy_and`)

### 影像來源

13. **HLS(YouTube / m3u8)的時間戳不能用牆鐘。** HLS 是一次送一整段
    (2–5 秒)的影格,實測 60 幀、**串流時間 2.0 秒**的內容在 **0.2 秒的
    牆鐘**內全部抵達。本系統判「這是抽菸一口還是扶眼鏡」完全靠停留秒數
    (`HandToMouthCounter` 的 2–5 秒窗),用牆鐘會把 2 秒的動作記成 0.2 秒,
    判準直接失效。`VideoSource.use_pts` 對 youtube/http 改用串流 PTS。
    RTSP 與攝影機維持牆鐘(逐幀即時抵達,牆鐘≈PTS,那條路實地測過不動)。

14. **PTS 跨重連會歸零。** 重連後 `CAP_PROP_POS_MSEC` 從 0 重新起算,
    時間一倒退,狀態機的視窗裁剪就永遠裁不掉舊紀錄、停留時長算成負數,
    整條鏈默默壞掉。`_MonotonicClock` 補偏移保證單調遞增。

15. **yt-dlp 解析出來的 manifest 網址會過期**(數小時,有時更短)。
    重連一定要**重新解析**,不能沿用舊網址——沿用的話重連永遠失敗,
    而且錯誤訊息看起來像網路問題。另外重連呼叫 yt-dlp 是網路 I/O、
    **會丟例外**,讀取執行緒必須接住,否則執行緒靜靜死掉,外面只看到
    「read 一直逾時」,毫無線索。

16. **HLS 要用佇列收幀,不能用「只保留最新」。** 這兩者對應兩種串流行為:
    RTSP 逐幀等間隔抵達(留最新、丟舊幀,延遲不累積是對的);HLS 一次送
    一整段。用錯的代價實測過:一個 burst 送 60 幀進來,消費端只撈得到
    2–3 幀,**其餘連同約 2 秒的內容整段丟掉**,30 fps 的來源有效取樣剩
    2 fps。改成佇列後同一條件下 4–5.7 fps,而且時間軸不再有洞。

17. **抽稀不可以做兩次。** 收幀端抽到 10 fps 後,相鄰幀在 30 fps 網格上
    的間距**剛好**是 0.1 秒;呼叫端若再判「間隔 ≥ 0.1」,浮點誤差
    (`0.7 - 0.6 = 0.09999999999999998`)會讓三分之一過不了,實測 30 幀
    掉到 20。`VideoSource.pre_sampled` 就是在講「已經抽好了,別再濾」。
    測試 `test_double_filtering_would_lose_a_third_of_frames` 釘住這件事。

18. **囤了緩衝就一定要節流,否則等於沒囤。** 消費端每秒跑得動 30 幀,
    直播每秒只生得出 10 幀 —— 不節流的話它會全速衝向直播邊緣,把囤好的
    5 秒在一兩秒內燒光,然後回到「每幀都要等」。實測:佇列從 62 掉到 3,
    每 5 秒仍卡一次。

19. **節流要用「存量水位」當訊號,不能用絕對時刻表。** 第一版寫成「這一
    幀該在 `wall0 + Δt` 供應」,結果佇列滿時 drop-oldest 讓下一幀的時間戳
    往前跳,節流誤以為自己超前 → 睡更久 → 丟更多 → 跳更遠,**正回饋
    螺旋,實測掉到 1.0 fps**。改成「存量 > 目標就全速、≤ 目標才放慢」
    之後沒有這個問題:丟棄會讓存量下降,而存量下降是**加速**的訊號。
    節流的 sleep 一定要在鎖外面 —— 握著條件變數睡會把收幀執行緒一起擋住,
    正好毀掉想保住的那段存量。三件事都有測試釘住(`TestPacing`)。

    串流最終數字(YouTube 街景直播,90 秒):
    最新幀策略 2.0 fps → 佇列 8.0 fps → +囤 5 秒 9~10 fps(卡頓 18 次)
    → +水位節流 **9.6~12.2 fps(卡頓 3 次)**。

20. **GUI 畫面重繪會餓死收幀執行緒。** 重繪跑在 Tk 主執行緒且持有 GIL,
    實測 800×600 要 5.8 ms、**放大到 1600×900 要 21.5 ms**。不設上限的話
    光畫圖就吃掉大半個主執行緒,串流因此掉幀。`DemoGUI.DRAW_INTERVAL`
    把重繪限在 15 fps;**推理不受影響**,限的只是顯示。
    狀態列會顯示實際 fps / 佇列存量 / 落後比,卡的時候看得出是來源餵不夠
    還是機器跑不動,不用猜。

21. **調低 `stream.max_height` 不會變快。** YOLO 內部一律縮到 imgsz=640,
    實測 720p 與 480p 的 `detect` 都是 27 ms,只差解碼那 2 ms。
    串流卡的真正原因是 YOLO 與收幀執行緒搶 CPU/GIL:收幀端單獨跑有
    13 fps,加上推理就掉到 4 fps。要再快得動偵測器(FP16 等),
    **但那會改變偵測數值,連帶動搖各方法的比較基準,不要順手改**。

22. **`subprocess` 的 stderr 千萬不要接 `PIPE` 然後沒人讀。** 沒人讀的
    管線只有 64 KB,ffmpeg 一寫滿就**卡在寫 stderr 上不動了**。實測錄了
    118 秒只寫出 19 秒、檔案剛好停在 4 MiB,**而且行程還活著**,從外面看
    像是「正在錄」——這種故障最難察覺。`recorder.py` 一律把 stderr 導進
    `<site>/ffmpeg.log`(檔案沒有大小限制,而且留下可查的紀錄)。

23. **錄影一天 30 GB。** 720p 實測 21 MB/分,保留 3 天要約 90 GB。
    本機 C: 只有 14 GB 可用,預設的 `--root recordings` 會在約 11 小時內
    把系統碟灌爆(E: 有 477 GB、D: 有 125 GB,`--root` 指過去)。
    磁碟滿的時候 ffmpeg 只會安靜地停住,所以啟動時就印出可用空間與預估。

24. **公開街景直播不是本系統的目標畫面。** 人小、多半背向,骨架分支會
    大量棄權(`min_scale_px: 24`)。拿來驗「管線跑不跑得動」很好用,
    拿來驗「準不準」沒有意義。

25. **FFmpeg 的 `Cannot reuse HTTP connection` 洗版壓不掉**(在本機的
    OpenCV 5.0.0 上):`OPENCV_FFMPEG_LOGLEVEL` 與
    `OPENCV_FFMPEG_CAPTURE_OPTIONS=http_persistent;0` 都實測無效,
    訊息是 FFmpeg 在 C 層直接寫 fd 2。訊息本身良性。處理方式是
    `啟動GUI.bat` 把 stderr 導進 `logs/gui_stderr.log`。

### 平台

26. Windows + PyTorch:`KMP_DUPLICATE_LIB_OK=TRUE`(OMP Error #15)。
27. `cv2.imread/imwrite` 不吃中文路徑,全專案一律走 `utils.imread/imwrite`。
28. Tkinter:固定格數面板要 `pack_propagate(False)`(`grid_propagate`

## 9. 設計決策與理由(不要好心改壞)

以下都是刻意的選擇,不是疏漏。要改請先確認理由已經不成立。

| 決策 | 理由 |
|---|---|
| 圖流**不做**旋轉對齊 | 攝影機固定俯視,人朝哪邊站本身是資訊(背對時腕-鼻距離無意義),旋轉掉會洗掉它。旋轉不變性由另一條運動學流提供 |
| 節點只取 13 個(砍膝踝) | 判別動作全在手臉之間;腿部在辦公室常被桌子遮擋,留著只是噪聲 |
| 加「功能邊」腕↔鼻/耳/眼 | 不是骨頭,但正是本任務的判別關係;加進圖裡訊息一步就傳到,不必繞腕→肘→肩→鼻四層 |
| 淺層標籤用規則不用人標 | 「舉手」就是腕-鼻距離在縮小,公式比人準也比人一致;而且標籤免費、隨資料自動變多 |
| 方位用單位向量不用角度 | 避免 ±180° 跳變 |
| L2 位置編碼編**真實秒數**不是序號 | 兩段停留差 2 秒還是 40 秒,是抽菸與否的關鍵 |
| L2 用 Transformer 不用 GRU | 判準是「兩兩之間像不像」(抽菸每口長得幾乎一樣),自注意力天生在算兩兩關係 |
| 節律統計做成手工特徵直接接分類頭 | 要 Transformer 從十幾個 token 自己學出「變異係數」這種二階統計,現有資料量不現實 |
| 在場型態(經過/徘徊/等待)**刻意不用模型** | 幾何上就是確定的;用模型只會把「隨時能調的門檻」變成「要重訓才能改的權重」 |
| 通報用次數主導,不用加權融合 | 純加權時次數分上限 0.8 → P 上限 0.32,永遠過不了 0.6 觸發線,「N 次通報」形同虛設 |
| 2026-08 把「手碰臉」拆成扶眼鏡/抓頭髮/其他碰臉 | 舊版合併是對的——在**逐幀攤平特徵**上它們確實是同一團點。但深層看的是**片段**:扶眼鏡「眼睛高度、0.5–1 秒、幾乎不動」vs 抓頭髮「眼睛以上、1–3 秒」,在「位置×時長×速度」空間分得開。判準沒變,變的是特徵解析度 |
| 「擦臉 vs 摸鼻子」仍然合併 | 人標的時候自己就會猶豫,標籤先天不一致 |
| 深層詞彙沒有「吃東西」 | 使用者指定的五類裡沒有。`eating` 可以標但不進 L2 訓練。它是最容易跟抽菸混淆的手到嘴動作,**要加只需在 `taxonomy.py` 的 `DEEP_CLASSES` 補一格、`DEEP_MERGE` 補一行** |
| 方法做成**登錄表**而不是 GUI 裡的 if/else | 使用者要求所有方法共用同一支 GUI(論文要橫向比較)。登錄表讓「新增方法」只動一個檔案的一格,介面自動長出來;寫 if/else 遲早會出現「選單有這個選項但管線沒接」的不一致 |
| 預設方法是**純規則** | 它不需要任何權重檔,`clone` 下來就能跑;而 `hybrid` 的實地表現是「57 段警報幾乎全為誤報」,不該當預設 |
| 純外觀網路方法 `count_gate=False` | 基準線要乾淨。若還套「手到嘴 3 次」的規則閘門,那條線量到的其實是規則的功勞 |
| 方法自己覆寫 `skeleton.enabled`(`Method.apply`) | 選了純規則卻載到 `skeleton.enabled: false` 的設定檔,會變成沒有任何階段來源、P_t 永遠 0 的**靜默失敗**——這種錯最難查 |
| 複核取**過去** 90 秒,不等未來影格 | 紅色警報要 ≥3 次手到嘴加 sustain 秒才成立,證據早就落在過去。等未來只延後結果,換不到新資訊 |
| 複核的「無法判斷」獨立成 `abstain`,不併入降級 | 47% 的片段骨架不可用。併入降級等於因為鏡位不好就壓掉真警報,正是這個模組被禁止做的事 |
| 降級門檻(`min_smoking=0.25`)刻意比升級寬 | 誤降一次真警報的代價遠高於多留一個橘色待複查。第二階段是過濾器,不是否決者 |
| 舊的 `stage2/model.py`(攤平 PoseTCN)保留不刪 | 當對照組。`normalize.py`、`dataset.py`、`train_m2.py`、`tests/test_stage2.py` 只服務它,動兩層模型時不用管 |

## 10. 檔案地圖

```
configs/        yaml 設定(model / train / inference,超參數零寫死)
models/         backbone、ring_buffer(通道排列唯一定義)、temporal_head、full_model
tracking/       YOLOv8(-pose) 偵測、ByteTrack、ROI 平滑裁切
inference/      即時管線、狀態機/計數器/移動閘門/在場型態、骨架分支、警報、RTSP
  methods.py    判定方法登錄表 ← 新增方法只改這裡(GUI 選單/--method 的唯一來源)
  verifier.py   第二階段複核:節點窗重取樣、降級不否決的 decide()
data/ training/ eval/    第一階段的資料前處理、訓練、評估
scripts/        gui.py、demo.py、label_tool.py、make_demo_videos.py、smoke_test.py
annotations/    clip_labels.json(片段標籤)、pose/*.npz(節點序列)
tests/          210 個測試
docs/           本文件、兩層模型設計、系統說明書、報告、簡報大綱

stage2/  ← 第二階段,兩層骨架時序模型
  graph.py         拓樸圖:節點、解剖邊/功能邊、分區鄰接矩陣
  kinematics.py    身體座標系、圖節點特徵、可解釋運動學量
  primitives.py    基元詞彙、規則偽標籤、分段、手到臉循環
  stgcn.py         時空圖卷積積木
  hier_model.py    L1 PrimitiveNet、L2 CompositionNet
  composition.py   token 組裝、節律統計、片段文法、說明文字
  hier_dataset.py  L1/L2 資料集與增強
  train_l1.py      淺層訓練(不需人工標籤)
  train_l2.py      深層訓練(需片段標籤;會自動跟文法基線比較)
  infer_hier.py    端到端推論介面 HierarchicalRecognizer
  taxonomy.py      標記類別表 + 深層類別對應
  extract_pose.py  警報片段離線回抽節點序列
  model.py / normalize.py / dataset.py / train_m2.py   ← 舊版攤平 PoseTCN(對照組)
```
